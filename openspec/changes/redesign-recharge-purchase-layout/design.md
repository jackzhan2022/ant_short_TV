## Context

当前 `/recharge` 使用 `commercial/index.tsx` 加载目录、当前会员、排队订阅、订单、余额和统一积分流水。页面通过「购买套餐」打开 `PurchaseModal.tsx`，弹窗将积分包与四种会员周期并列，点击某张卡片的订购按钮立即创建订单。权益第一项既作为摘要又出现在列表中，因此重复。

用户选择的视觉方向是「品牌旗舰」，之后补充了会员套餐与积分包的双入口。已将最新原型冻结在 [references/purchase-layout.html](references/purchase-layout.html)：以其中 `data-variant="品牌旗舰"` 为视觉参照；「轻盈商务」仅保留为设计历史，不进入产品的布局切换功能。原型里的示例会员、套餐改名、团队余额和会员日期均不构成生产数据。

现有合同涉及 `subscription-package-management`、`team-subscription-entitlements`、`commercial-order-payment` 与 `recharge-point-history`。会员属于团队，已发放积分永久有效；不同档位排队生效。页面重排不能改变这些规则。当前可售目录可能没有任何会员商品，产品仍需保留会员入口及明确空态。

## Goals / Non-Goals

**Goals:**

- 在充值页主视野完成类别选择、会员周期筛选、真实商品比较和订单确认。
- 落实品牌旗舰的视觉层级，同时适配任意数量的后台商品、长名称、空目录和窄屏。
- 明确展示会员的周期权益与积分包的一次性权益，避免示例数据和重复文案进入正式页面。
- 保留现有权限、扫码付款、待支付订单恢复、订阅摘要和积分流水体验。

**Non-Goals:**

- 不调整价格、权益、套餐发布状态、会员档位、自动续费或扣费规则。
- 不新增后端接口、数据库字段、推荐算法或外部 UI 依赖；现有混合会员的一次性积分履约需与目录承诺一致。
- 不将原型中的方案轮播、主题调节、假付款码和示例会员发布为业务功能。
- 不在本次提案阶段实现或部署页面。

## Decisions

### 1. 主选购区内嵌，付款步骤使用弹窗

在 `/recharge` 内依次呈现：品牌页头与团队余额、标题与当前会员摘要、双入口、会员周期与商品卡、订单确认条、订阅与订单、积分流水。页面保留返回工作台与查看流水的可达入口。支付二维码仍在独立弹窗中呈现。

采用该结构是因为原型要求在同一视野比较商品和确认金额。仅美化原来的大弹窗虽然改动更小，但保留了入口隐藏与上下文分离的问题；新建额外购买路由会增加当前团队与待支付订单的状态同步成本。

### 2. 按业务类型分组，按真实周期筛选

首屏默认 `membership + monthly`，两个一级入口始终可见。会员周期使用月、季、半年、年四个控件。分类只依据 `packageType`，积分包不会因自身 `billingPeriod` 值进入会员列表。

会员以有效 `periodMonths` 的 1、3、6、12 归类；缺失时才用已知 `billingPeriod` 映射。两者不一致时以有效月数为准；未知或不支持的周期列入独立的「周期信息待确认」提示区，保留商品名称但禁用购买，不能默认当作月卡。周期总积分和折合月价只在有效月数存在时推导。

每个类别/周期维护最后一次选择的 `packageVersionId`。返回某分组时恢复仍然有效的选择，否则按接口顺序选中第一项。空分组清空摘要并禁用付款；即使全部会员下架也不隐藏会员入口、不自动切到积分包。这里不提供后端不存在的档位、示例商品或售卖价格。

### 3. 权益由类型映射，选择状态与营销标签分离

独立展示辅助函数处理 `CommercialCatalogItem`：

- `PERIODIC_POINTS`：每月额度及「周期发放合计 = 每月额度 × 有效月数」，明确按月发放，不能表示为一次到账。
- `ONE_TIME_POINTS`：积分包的一次性额度；会员同时包含该项时单独标为一次性发放，不混进每月额度。
- `GLOBAL_DISCOUNT`：按真实数值显示积分折扣；缺失时不显示默认折扣。
- `DISPLAY`：保留权益名称快照，不添加虚构数值或功能承诺。

用于醒目摘要的权益不在下方完整复述；其余权益逐项展示。只有有效非负价格和正积分数量才能计算单位积分价格；只有 `listPrice > price` 才展示划线原价与优惠标签。货币来自商品数据。

现有后端允许会员配置 `ONE_TIME_POINTS`，但原履约路径只给积分包发放该权益。会员混合权益因此可能造成展示承诺与到账不符。付款后对任何包含 `ONE_TIME_POINTS` 的订单按订单 ID 发放一次，随后处理会员激活与周期积分；排队会员的购买赠送积分立即发放，续费的新订单各发放一次，重试沿用原订单幂等键。该修正不改变目录、价格或既有周期积分规则。

零额度积分不作为可到账权益展示。后端对零额度一次性积分不调用入账；零额度周期积分保留周期发放进度记录但不写积分账本，避免可发布的零值配置使付款订单或后续定时发放永久失败。未知商品类型在创建时拒绝，历史异常类型也不能静默履约成功。

积分包不能兑现会员专属的 `PERIODIC_POINTS` 或 `GLOBAL_DISCOUNT`。新建草稿与发布时拒绝这种组合；历史异常版本不进入可售目录，下单时再次拒绝。若旧目录响应仍包含异常积分包，前端保留名称但禁用购买，并隐藏不能兑现的周期/折扣承诺。

原型深色金色卡用于当前选中方案，标记为「已选方案」。现有接口没有推荐字段，因此不把有折扣、列表首项或示例套餐擅自称为推荐。后台商品名称原样显示，不替换为原型的「轻量体验」「团队创作」。

### 4. 分离选购状态、提交状态和支付订单

页面持有三个独立状态：

| 状态 | 内容 | 触发的网络行为 |
| --- | --- | --- |
| Selection | 类别、周期、有效商品版本 | 切换本身不发送下单请求 |
| Submitting | 确认时的团队和商品快照、提交锁 | 单次显式确认调用创建订单 |
| Payment | 已返回的订单 ID、金额、二维码、有效期 | 继续既有查单轮询 |

支付按钮在无商品、无购买权限或提交中时不可用，同时通过同步提交锁避免快速连击。创建请求只携带选中版本 ID，金额由服务器确定。业务失败直接显示原因；网络结果不确定时先读取待支付订单，不自动重发 POST。目录变更导致商品不可售时刷新目录并要求重新确认。

创建订单时后端还需重新检查商品的 `effectiveFrom <= now < effectiveTo` 生效窗口，与目录筛选一致；已过期或未生效的已发布版本也必须拒绝，不能依赖浏览器中较早读取的目录。

二维码在本地到期时先查服务端，避免遗漏临界点的成功支付；若服务端仍待支付则隐藏过期码并继续核对，直到服务端返回终态。`ENTITLEMENT_PENDING` 表示付款已确认但权益仍在重试，关闭二维码并持续跟踪，只有 `COMPLETED` 才提示权益到账和刷新账户数据。
支付弹窗自身按本地计时隐藏过期二维码，即使查单请求失败，也不继续展示无法使用的付款码。

付款弹窗显示订单返回的金额、币种、有效期及二维码，不随后台选购区切换重新计价。新订单保存确认时的展示名称；恢复历史待支付订单时，现有 API 没有商品名称，使用「套餐订单」和商户订单号，不借用当前选中商品的名称。服务器确认支付完成、失败或关闭，以及用户关闭弹窗、离开页面或更换团队时，结束旧订单跟踪；本地二维码到期仅隐藏二维码并继续等待服务器终态。可恢复的待支付订单仍保留「继续支付」。任何积分/会员成功提示都以服务端最终结果为准。

### 5. 团队隔离与账本区域保留

团队切换时清理选择、提交引用、支付弹窗与计时器，再读取新团队数据；使用请求序号或取消标记丢弃旧团队的迟到响应。成功支付后刷新当前会员、排队订阅、订单、余额和唯一一份积分流水。

订阅与订单、积分明细放在主选购区下方，继续使用既有数据源，不复制商业权益发放列表作为第二份流水。日期按应用约定的本地格式展示，缺失或不可解析时显示占位，不展示原始 `T` 分隔日期或伪造下一次发放时间。

### 6. 组件与视觉实现边界

- `index.tsx`：页面数据加载、团队隔离、订单提交/查单生命周期和账户信息。
- 新建 `PurchasePanel.tsx`：内嵌类别、周期、商品卡与确认条，使用受控选择状态。
- 将 `PurchaseModal.tsx` 收敛为 `PaymentModal.tsx`：二维码、倒计时和关闭/返回操作；相应迁移旧测试，避免残留两个选购入口。
- 新建 `purchasePresentation.ts`：分组、权益摘要、货币/日期/单位价格等纯展示计算及对应测试。
- `backend/.../CommercialEntitlementOrchestrator.java`、`CommercialSubscriptionGrantService.java`：修正会员一次性及零额度积分的履约，复用现有事务与幂等键。
- `backend/.../CommercialOrderService.java`、`CommercialPackageService.java`：确认时检查真实生效窗口，并拒绝未知商品类型与无法履约的积分包权益组合。
- `index.less`：沿用现有页面样式体系，局部定义品牌旗舰语义 token；复用 antd 控件，不引入可视化运行时或修改自动生成 services。

桌面采用最大内容宽度约 960–1040px、24–36px 页面留白，商品卡支持自适应列数；选中卡使用炭黑表面与香槟金信息，支付操作沿用品牌色。当前会员信息和余额为紧凑摘要，明细不抢占首屏。手机端卡片与确认条纵向排列，长名称、金额和错误信息正常换行，无固定页高或遮挡式底栏。二级周期控件在窄屏换行；保证明确的选中态、键盘操作、焦点可见和支付弹窗焦点管理。暗色模式使用相应产品语义 token，不能依赖单一亮色背景维持对比。

备选方案是直接复制原型 HTML/CSS；它包含演示数据、方案轮播与运行时脚本，不适合作为生产组件，因此只作为视觉基准。

## Risks / Trade-offs

- [会员目前可能全部下架] → 会员入口保留，空态说明当前周期无可售商品，并允许显式切到积分包；不为了截图效果填充商品。
- [目录中的周期字段可能不一致] → 统一月数优先规则及异常周期提示，金额和权益计算有输入校验。
- [预览的价格/权益被误当业务配置] → 冻结参考文件仅用于视觉；生产代码仅消费真实接口，测试以 fixture 覆盖各种状态。
- [会员同时有一次性与周期权益] → 两类积分分别标识，周期总量不承诺提前到账。
- [点击卡片或重复点击造成额外订单] → 选择与提交分离、提交锁、明确恢复待支付订单，失败不自动补单。
- [已下单商品随后下架或用户换团队] → 已有订单按服务端金额继续展示，隔离请求作用域并停止旧轮询。
- [品牌旗舰深色卡影响对比/移动布局] → 320px、390px、768px、1440px 下验证真实字体、长内容与深浅模式；按原型截图复核层级而不硬套尺寸。

## Migration Plan

1. 使用本变更的规范和冻结参考实现前端组件，保留 API 与路由契约。
2. 通过展示辅助函数测试、组件测试和购买/支付生命周期回归；运行 `npm run lint`、`npx antd lint ./src`、`npm run build`。
3. 在本地或测试环境使用确定性目录与支付桩验证交互、响应式和截图；线上只做无下单的页面/资源/数据加载检查，真实付款验收另按当次用户授权执行。
4. 未来发布时保留上一版前端制品。该变更无数据迁移，回退前端即可恢复旧布局，已创建订单继续由既有后端处理。
