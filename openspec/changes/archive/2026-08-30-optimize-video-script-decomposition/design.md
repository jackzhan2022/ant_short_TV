## Context

视频拆剧已经采用一次视频理解调用直接返回 `{"script":"..."}`，正常成功路径将 `script` 写入 episode 的草稿字段并进入 `PENDING_REVIEW`。页面随后允许编辑、保存、选择项目并确认导入 `ScriptVersion`；与此同时，历史的 `DRAFT_GENERATION` 文本模型路径仍可通过重生成入口触发。该状态机使“模型生成完成”“用户审核完成”和“项目导入完成”混为同一批次进度，也使正常生成与重生成使用不同模型。

本变更以租户级独立视频拆剧为边界。一个批次包含有序视频，每个视频只产生一个不可变剧本结果；失败可以技术重试，成功后再次生成必须新建批次。批次级“合并”仅是按集号聚合查看，不产生新的模型调用或持久化文本。

## Goals / Non-Goals

**Goals:**

- 将新批次收敛为单阶段视频理解直接生成剧本，并在成功时完成任务和计费。
- 以独立、只读、可追溯的数据记录保存每个视频的剧本结果，不耦合项目剧本版本。
- 提供准确的批次计数、百分比和单集阶段进度，并支持未完成批次实时查看。
- 提供按集号逐集查看、复制全部可用剧本的聚合界面。
- 固化适合当前产品的 Markdown 中文拍摄剧本格式并进行确定性结构校验。
- 保留历史草稿、确认、项目绑定和遗留文本草稿生成任务的读取与执行兼容。

**Non-Goals:**

- 不接入或扩展新版 Workflow Agent。
- 不调用模型合并、润色或改写多集剧本，不保存“合并剧本”。
- 不创建、更新或自动关联项目 `Script`、`ScriptVersion`。
- 不提供成功结果编辑、覆盖、版本切换或原批次主动重新生成。
- 不生成分镜、镜头语言或摄影参数。

## Decisions

### 1. 新结果使用独立的一对一结果记录

新增 `video_decomposition_script_result`（最终命名遵循现有 Flyway/实体约定），至少包含 tenant、batch、episode、analysis/call evidence、content、format version、created time，并对 episode 建唯一约束。成功解析与结果插入在同一事务边界完成，插入后业务 API 不提供 update/delete 操作。episode 保存 result id 或通过唯一 episode id 查询，状态直接进入 `SUCCEEDED`。

选择独立结果记录而不是继续复用 `draft_content`，因为后者携带可编辑、版本递增、待审核和确认导入语义。历史字段与接口响应保留为兼容读取，不迁移或删除用户已有内容。

### 2. 新批次只走视频理解单阶段，遗留草稿阶段隔离保留

新 episode 状态收敛为 `PENDING_ANALYSIS`、`ANALYZING`、`SUCCEEDED`、`FAILED`，执行 phase 固定为 `VIDEO_ANALYSIS`。成功后不再设置 `PENDING_REVIEW`，也不创建 `PENDING_DRAFT`。调度器仍识别部署前已存在的 `PENDING_DRAFT` / `DRAFT_GENERATING`，但前端不再为新结果提供“重生成草稿”。

这延续现有 direct-video-script-output 的单次计费合同，避免为同一视频再引入文本模型、第二次积分预占或不一致的提示词。

### 3. 传输协议与用户剧本文本分层

供应商响应继续使用稳定协议 `{"script":"完整剧本文本"}`，以便识别空输出、非 JSON 和截断；用户看到和复制的只有 `script` 纯文本。提示词要求如下 Markdown 结构：

```text
# 第1集：标题

## 1-1 夜 内 地点

出场人物：人物A、人物B

动作与环境段落。

角色名
（可选的神态、动作或语气）
对白，不加引号。

角色名
（OS）
画外音或内心独白。

——本集完
```

每场必须有与当前 episodeNo 一致且连续递增的场号、时间、内/外景、地点和出场人物。拉丁字符角色提示统一大写，中文名保持原样；OS/VO 使用全角括号。动作只描述视频可见或可听证据，保持事件顺序。若视频本身以悬念结束，直接还原最后动作或对白；不输出 `结尾钩子：` 标签，也不为无悬念视频编造情节。

解析器在现有 JSON/非空校验之后执行轻量结构校验：集标题、至少一个合法场景头、每场出场人物、连续场号和结束标记。结构失败记为 `AI_RESPONSE_INVALID` 并允许技术重试。它不判断剧情质量、姓名准确性或事实真实性。

### 4. 技术重试与主动再生成严格分离

原批次只允许 `FAILED && retryable` 的 episode 重试。技术重试新增 attempt，但沿用同一 execution version、模型、价格和幂等身份；成功、运行或等待中的 episode 均拒绝重试。用户对成功剧本不满意时创建新批次，从而获得新的 task、execution version 和当时有效的模型/价格配置。

这比在同一 episode 维护生成版本更简单，也符合“一个批次只代表一次生成意图”的产品定义。

### 5. 批次进度由 episode 执行状态聚合

批次响应增加或明确 `succeededEpisodes`、`failedEpisodes`、`processingEpisodes`、`pendingEpisodes`、`progressPercent`，并保证分类计数之和等于 total。总体百分比取所有 episode 执行百分比的算术平均；未创建/未开始为 0，成功为 100，失败保留终止时进度但不计为成功。

批次状态规则为：全部成功 `SUCCEEDED`；全部终止且全部失败 `FAILED`；全部终止且成功失败并存 `PARTIAL_FAILED`；其他存在运行任务为 `RUNNING`；尚未运行时为 `PENDING`。历史批次继续映射旧状态供读取，但新批次不再以待审核或已确认为完成条件。

### 6. “查看全部剧本”是读取时聚合

新增或扩展批次详情 API，一次返回按 episodeNo 排序的轻量 episode 状态和成功 screenplay content。页面可在批次运行中打开：成功项渲染 Markdown；等待/运行项显示 phase 与 percent；失败项显示错误和重试。复制全部功能仅在浏览器内按 episodeNo 拼接当前成功内容，不创建服务端记录。

不把所有内容塞入批次列表响应，避免列表查询加载大量 LONGTEXT。列表只返回计数和进度；用户打开批次全部剧本视图时再获取内容。

### 7. 页面移除伪流程和写操作

创建区域删除顶部四步 `Steps` 与整体 `Progress` 及其派生状态。批次列表保留真实计数、状态和百分比，并提供“查看全部剧本”。单集/聚合详情均只读；移除保存草稿、重生成草稿、确认导入、项目选择和查看已导入版本入口，仅失败且 retryable 的单集显示重试。

历史批次详情可以展示“历史草稿/已导入”只读标记，但不继续暴露会改变项目剧本的旧动作。

## Risks / Trade-offs

- [模型偶尔输出接近但不完全符合 Markdown 结构] → 提示词提供完整模板，解析器返回明确结构错误并允许技术重试；校验保持轻量，不验证文风。
- [一次响应可能因长视频或输出 token 上限截断] → 同时检查协议完整性、provider finish reason 和结束标记；截断结果不落库并保留 raw response。
- [聚合页面加载大量剧本文本] → 列表与内容 API 分离；批次内容按需加载，前端逐集折叠渲染，必要时后续增加分页而不改变存储合同。
- [历史与新状态并存增加分支] → 以结果记录/批次创建版本或等价可判定条件区分新旧流程；集中维护状态映射并覆盖迁移测试。
- [成功结果不可编辑可能放大少量识别错误] → 这是本次明确产品边界；用户通过新批次重新生成，未来显式编辑/导入能力单独设计。
- [失败进度纳入平均值可能造成百分比不再增长] → 同时展示成功、失败、处理中计数；终态批次以状态和计数为准，不把 100% 等同于全部成功。

## Migration Plan

1. 新增独立结果表、唯一约束和必要索引，不修改或删除历史草稿及确认字段。
2. 部署后端兼容读取和新响应字段，再切换新批次成功路径写独立结果并进入 `SUCCEEDED`。
3. 保留调度器对历史 `PENDING_DRAFT` / `DRAFT_GENERATING` 的处理，验证旧任务可恢复。
4. 部署前端真实进度、聚合查看和只读详情，移除新流程的审核/导入动作及顶部步骤条。
5. 使用多视频批次验证并发执行、部分失败、失败重试、全部成功、聚合顺序、Markdown 渲染和复制。

回滚时恢复前端旧入口和新 episode 的旧状态写法，但保留独立结果表及已生成内容。不得删除已落库结果；若旧版本无法读取结果表，可通过兼容脚本将 content 回填到历史 `draft_content` 后再切换应用版本。
