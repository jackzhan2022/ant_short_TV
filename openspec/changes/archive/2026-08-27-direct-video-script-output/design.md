## Context

视频拆剧当前分两阶段：视频理解模型必须产出 `characters`、`scenes`、`props`、`timeline`、`dialogue`、`actions`、`emotions` 七个数组，标准化后再调用文本模型生成剧本草稿。实际消费者只保存完整 JSON 并把它传给第二个模型；数组不会分别进入草稿保存或确认导入流程。现有草稿保存、版本校验和确认导入都以 `draft_content` 为边界。

新流程必须减少模型输出和调用次数，同时不能中断已经进入 `PENDING_DRAFT` 的历史任务。

## Goals / Non-Goals

**Goals:**

- 让视频理解模型以用户指定的专业短剧格式直接生成完整剧本。
- 使用最小 JSON 包装 `{"script":"..."}` 保持提供商 JSON 输出约束，并在服务端校验 `script` 非空。
- 将 `script` 直接存入 `draft_content`，令新任务进入 `PENDING_REVIEW`，可继续编辑、保存及确认导入。
- 仅为视频理解阶段保留执行、计费、调用日志和尝试记录。
- 允许历史 `PENDING_DRAFT` 任务继续使用已有文本草稿生成路径。

**Non-Goals:**

- 不改变草稿保存、确认导入、剧本版本或前端编辑接口。
- 不迁移或重写已有成功/失败分析记录。
- 不删除旧草稿生成 Agent 或旧任务恢复逻辑。

## Decisions

### 使用 `script` 单字段 JSON 协议

视频理解响应定义为 JSON 对象，且 `script` 必须是非空字符串。模型仍受到 JSON 输出约束，避免非结构化响应难以诊断；但不再要求无下游用途的七个数组。

备选方案是允许纯文本响应。未采用，因为当前视频调用适配器和诊断记录以 JSON 响应为边界，单字段 JSON 既减小内容负担，也保留可验证协议。

### 将视频理解结果直接落为草稿

视频分析标准化结果暴露 `script` 和标准化 JSON。视频分析成功后，同一个视频分析执行将 `script` 写入 `draft_content`，递增 `draft_version`，清空执行占用，并将 episode 设置为 `PENDING_REVIEW`。该执行以视频分析成功结算，结果类型指向 episode。

备选方案是保留第二次文本调用但将 `script` 作为输入。未采用，因为它重复改写同一内容，会增加时延、失败面和计费，且不能保证保留用户要求的格式。

### 对历史任务进行状态隔离

仅 `PENDING_ANALYSIS` 的新分析使用直出草稿逻辑。已有 `PENDING_DRAFT` / `DRAFT_GENERATING` 任务继续进入旧的 `executeDraftGeneration` 路径，避免升级期间已有工作被卡住。

### 用提示词保证剧本格式，而不是字段拆分

`video-understanding` Agent 提示词将要求按集数与标题、场景标头、视听动作和环境、人物对白与字幕、结尾钩子逐镜头还原，并将该完整文本放入 `script`。这保留用户定义的内容质量标准，同时缩短响应结构。

## Risks / Trade-offs

- [视频模型仍返回非法 JSON 或空剧本] → 标准化器拒绝该响应，记录原始响应和调用日志，并将任务标为可重试失败。
- [直接视频模型的剧本文本质量低于专用文本改写模型] → 在提示词中固定专业格式，用户仍可在待审核草稿中编辑、保存和确认导入。
- [部署期间存在历史草稿阶段任务] → 保留旧阶段处理，不把历史状态路由到新协议。
- [调用/计费报表假定两个阶段] → 测试确保新任务只保留一个视频分析执行；历史任务的第二阶段记录不受影响。

## Migration Plan

1. 部署后，新建或重新分析的任务按 `script` 协议执行。
2. 已在 `PENDING_DRAFT` 或 `DRAFT_GENERATING` 的任务继续使用旧文本草稿生成逻辑。
3. 如需回滚，恢复旧版服务即可；已完成的新草稿仍在既有 `draft_content` 中可编辑和确认，无需数据回滚。

## Open Questions

- 无。当前不新增用户可配置的格式开关；提示词按已确认的专业剧本格式内置。
