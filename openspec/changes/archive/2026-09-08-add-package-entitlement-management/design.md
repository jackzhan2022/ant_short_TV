## Context

套餐版本目前将权益直接保存到 `commercial_entitlement`，并只接受一次性积分、周期积分和全局折扣三种带数值的运行时权益。表中已经预留 `text_value` 和 `config_json`，但没有可供运营维护的权益目录，前端套餐表单也只能从三个硬编码选项中选择。购买页和订单快照均依赖套餐版本返回的权益，因此新增展示权益必须保持版本不可变，并且不能被现有发放、折扣解析或模型路由误当成可执行能力。

本变更涉及套餐管理前后端、数据库迁移、商品目录响应和购买页展示。平台运营人员是权益目录的维护者，团队购买者是展示权益的消费者。

## Goals / Non-Goals

**Goals:**

- 在套餐管理页增加“权益管理”Tab，统一查看系统权益和维护展示权益。
- 允许运营创建、编辑、启用和停用可复用的纯展示权益，例如“使用全部模型”。
- 套餐草稿从权益目录选择权益，并针对系统权益收集数值、针对展示权益只保存展示快照。
- 保持已发布套餐、订单和订阅中的权益名称稳定，不受目录后续修改或停用影响。
- 保证展示权益不会产生鉴权、路由、计费、积分发放或周期任务效果。

**Non-Goals:**

- 不实现“使用全部模型”等文案所描述能力的运行时控制。
- 不新增免费次数、并发数、成员数或模型范围等可执行权益。
- 不改变支付、订单、订阅、积分账本或全局折扣的状态机与算法。
- 不允许删除权益定义；停用用于阻止后续套餐版本引用，同时保留历史可追溯性。
- 不新增权限码，继续复用套餐查看和编辑权限。

## Decisions

### 1. 使用独立权益目录，并将套餐版本权益保留为快照

新增 `commercial_entitlement_definition` 表，字段包含稳定且唯一的 `code`、名称、说明、类别 `SYSTEM`/`DISPLAY`、状态 `ACTIVE`/`INACTIVE`、排序值和审计时间。迁移以幂等方式预置 `ONE_TIME_POINTS`、`PERIODIC_POINTS`、`GLOBAL_DISCOUNT` 三条系统定义。

`commercial_entitlement.entitlement_type` 继续保存稳定 code，系统权益继续使用 `numeric_value`；所有新建套餐版本同时将目录中的当前名称复制到 `text_value`。展示权益的 `numeric_value` 必须为空，其显示内容取 `text_value`。现有历史行不强制回填名称，读取时对三个系统 code 使用字段字典回退。

选择该方案是为了将“可复用的运营目录”和“不可变的商业快照”分离。仅在套餐版本中保存自由文本会造成重复录入和无法统一停用；运行时动态关联目录名称则会让历史订单展示随目录修改而变化。

### 2. 系统权益受保护，展示权益使用服务端生成的稳定 code

系统定义可以查询，但更新、停用和删除请求必须被拒绝。展示权益创建时由服务端生成不可变 code；运营只维护名称、说明和排序，并通过状态操作启用或停用。名称需要去除首尾空白且不能为空，同名是否允许由服务层按当前有效目录进行唯一性校验，以避免套餐表单出现无法区分的选项。

使用服务端生成 code 可避免运营输入与未来系统权益冲突，也能让改名不改变套餐引用。允许直接编辑任意 code 的替代方案被放弃，因为 code 已进入套餐、订单和订阅快照，是技术身份而非展示字段。

### 3. 套餐草稿按目录类别进行校验和持久化

套餐草稿请求继续使用权益 code 作为 `type`，并将 `value` 改为可空：

- `SYSTEM` 权益必须处于启用状态并提供符合原规则的数值。
- `DISPLAY` 权益必须处于启用状态且不得携带数值。
- 未登记 code、停用权益、重复权益或类别和值不匹配时，服务端返回明确校验错误。

创建草稿时立即保存 code、数值和名称快照；发布时再次确认草稿内引用的目录定义仍然存在且启用。这样，停用展示权益可以阻止尚未发布的草稿继续进入销售目录，而已经发布、下架或被订单引用的版本仍按自身快照读取。

仅在前端校验的替代方案被放弃，因为 API 调用方可以绕过页面，并且支付目录必须只暴露经过服务端验证的套餐。

### 4. 运行时只按明确的系统 code 执行

现有积分发放、周期积分和折扣解析继续仅匹配三个系统 code。展示权益不会写入 `commercial_entitlement_grant`，不会参与 `CommercialEntitlementResolver`，也不会进入模型访问判断。商品目录和套餐历史响应增加快照名称与类别，前端使用这些字段渲染；旧数据缺少快照时使用统一字段字典回退。

不引入通用“权益执行器”注册机制，因为本期展示权益没有运行时行为，提前抽象会扩大计费和鉴权风险。

### 5. 套餐管理页采用与模型管理页一致的 Tab 容器

顶层 `PageContainer` 下使用受控 `Tabs`，包含“套餐列表”和“权益管理”。现有套餐表格、版本抽屉和草稿弹窗下沉为套餐 Tab 内容，避免嵌套页面容器。权益管理 Tab 使用列表展示名称、code、类别、说明、状态和更新时间；系统权益操作区显示只读，展示权益按权限提供编辑及启停操作。

套餐表单从启用目录加载选项。系统权益选择后显示数值输入，展示权益选择后只显示名称和说明。购买页直接逐条展示版本快照名称；三个系统权益仍保留当前带数量或折扣格式的文案。

独立路由方案被放弃，因为用户明确要求参考模型管理页，并且套餐与权益是同一管理上下文。

### 6. API 与权限边界

新增平台权益目录查询、创建、更新和启停接口。查询复用 `PLATFORM_COMMERCIAL_ORDER_VIEW`，写操作复用 `PLATFORM_COMMERCIAL_PACKAGE_EDIT`，与现有套餐页可见性保持一致。所有写入均由服务端判断定义类别，客户端提交的 `SYSTEM` 标识不得改变保护规则。

## Risks / Trade-offs

- [展示文案可能被误解为真实能力] → 页面明确标记“展示权益”，后端完全忽略其运行时执行；产品上线前由运营确认文案真实性。
- [停用发生在草稿创建与发布之间] → 发布时再次校验目录状态，并返回具体的失效权益名称。
- [历史系统权益没有名称快照] → 读取时对三个固定 code 使用现有字段字典回退，不做破坏性历史更新。
- [目录改名造成新旧套餐展示不一致] → 这是版本快照的预期行为；新建版本使用新名称，历史版本保持原文案。
- [新增目录查询增加套餐表单请求] → 权益数量预期较小，进入页面时加载并在当前会话复用；后端按排序字段和 ID 稳定排序。

## Migration Plan

1. 通过 Flyway 新增权益定义表和唯一索引，并幂等插入三个系统定义。
2. 部署后端目录 API、套餐校验与扩展响应；旧前端仍可提交三个系统 code，保持向后兼容。
3. 部署带 Tab、权益管理和新套餐表单的前端。
4. 用三个系统权益和一个展示权益完成草稿、发布、购买目录及历史快照冒烟测试，并确认展示权益未产生发放记录。
5. 回滚应用时保留新增目录表和套餐权益快照数据；旧应用会忽略 `text_value`，但无法编辑包含展示权益的套餐，因此回滚期间应暂停相关套餐发布。

## Open Questions

无。展示权益明确为纯文案，本变更不赋予其任何运行时语义。
