## Context

系统已具备租户、租户成员、团队积分账户、商业套餐版本和团队订阅数据，但现有 `/api/tenants/*` 接口依赖有效租户成员上下文。平台运营人员既不能跨租户查询，也不能通过这些接口恢复已停用租户，因为停用状态会在租户上下文解析阶段被拒绝。平台商业化管理已有独立的平台权限和路由模式，本变更沿用该边界增加租户运营能力。

首期服务于具有平台权限的运营人员。页面需要在一次工作流中完成租户检索、关键经营信息查看和状态处理，同时避免暴露资料编辑、成员管理、套餐调整和积分调整能力。

## Goals / Non-Goals

**Goals:**

- 提供可分页、可筛选的平台租户列表和聚合详情。
- 展示租户基本信息、Owner、有效成员数、积分余额、当前套餐和待生效套餐。
- 允许具有独立状态管理权限的平台运营人员启用或停用租户。
- 允许平台恢复已停用租户，不依赖租户成员上下文。
- 对平台租户状态变更保留可审计记录。
- 保持列表查询次数随页数而非租户行数增长。

**Non-Goals:**

- 不修改租户名称、类型、Logo 或简介。
- 不查看完整成员名单或管理成员与角色。
- 不调整套餐、订阅、订单或积分。
- 不展示历史订阅、完整积分流水、项目或 AI 使用统计。
- 不改变团队 Owner 现有的租户设置接口及租户选择规则。

## Decisions

### 1. 使用独立的平台租户 API

新增以下平台接口：

- `GET /api/platform/tenants`：分页查询租户，接受 `keyword`、`status`、`packageType`、`current` 和 `pageSize`。
- `GET /api/platform/tenants/{tenantId}`：查询单个租户聚合详情。
- `PUT /api/platform/tenants/{tenantId}/status`：将状态设置为 `ACTIVE` 或 `DISABLED`。

接口使用平台权限校验，不调用 `TenantContextResolver.requireActiveMember`。查看接口要求 `PLATFORM_TENANT_VIEW`，状态接口要求 `PLATFORM_TENANT_STATUS_EDIT`。这样平台运营可以读取和恢复停用租户，同时不会被授予租户内业务权限。

替代方案是复用租户成员接口并为平台管理员添加绕过逻辑。该方案会混合平台权限与租户权限，增加越权风险，因此不采用。

### 2. 分页后批量聚合列表数据

查询服务先对未软删除租户执行筛选和分页，再针对本页租户 ID 批量查询 Owner、有效成员数、积分账户和有效订阅/套餐版本，并在服务层按租户 ID 合并。`packageType` 筛选通过有效订阅的存在性条件参与租户分页，避免聚合后过滤导致总数和分页不准确。

列表响应包含租户 ID、编码、名称、类型、状态、Owner 摘要、有效成员数、积分余额、当前套餐摘要、创建时间。没有积分账户或有效套餐时分别返回余额 `0` 和 `null`，前端显示 `0` 与“暂无套餐”。当前套餐摘要包含套餐 ID、版本 ID、类型、名称、订阅状态、开始时间和结束时间。

替代方案是前端逐行组合现有接口。该方案既无法通过租户权限校验，也会产生 N+1 请求，因此不采用。首期也不建立运营宽表，因为字段量与访问规模尚不足以抵消同步复杂度。

### 3. 详情复用同一聚合模型并增加待生效套餐

详情接口返回列表字段，并补充 Logo、简介、更新时间和按开始时间升序排列的 `QUEUED` 订阅摘要。详情不返回完整成员列表、订单或积分流水。套餐名称优先读取订阅快照；若快照不可解析，则回退套餐版本名称，保证历史快照与运营展示一致。

前端在租户列表中使用抽屉展示详情，以保留查询条件、页码和滚动位置。抽屉分为基本信息、账户摘要、当前套餐和待生效套餐四个无嵌套区域。

### 4. 状态设置采用幂等命令并记录审计

状态接口接收目标状态，而不是“切换”动作。目标状态与当前状态一致时返回当前结果且不重复写审计；状态实际变化时在事务内更新租户并写入操作日志。前端在停用和启用前均显示确认框，停用确认文案明确说明租户成员将无法进入团队业务。

现有 `operation_log` 增加可空 `detail_json` 字段，并扩展记录方法，用结构化内容保存 `previousStatus`、`newStatus` 和平台操作来源。操作代码使用 `PLATFORM_UPDATE_TENANT_STATUS`。状态变更不终止登录会话，但后续租户上下文解析会立即拒绝停用租户。

替代方案是在操作名称中拼接前后状态。该方式难以稳定查询和扩展，因此采用结构化详情。

### 5. 前端沿用商业化管理导航与权限模式

在 `商业化管理` 下新增 `租户管理` 子路由。`canViewPlatformTenants` 控制菜单和页面访问，`canEditPlatformTenantStatus` 控制启停按钮。列表使用 ProTable 的 `request` 分页模式，查询条件为关键字、状态和当前套餐类型；行操作为查看详情及启用/停用。所有新增菜单和页面文案补齐项目现有语言文件，中文为业务基准文案。

## Risks / Trade-offs

- [聚合查询随列表规模增长变慢] → 先分页租户，再按本页 ID 批量查询；为状态、成员租户 ID、订阅租户 ID/状态等查询条件复用或补充索引，并增加查询数量测试。
- [套餐快照格式异常导致详情失败] → 单条快照解析失败时回退版本名称，不影响整页租户查询。
- [运营误停用正在使用的租户] → 状态变更使用独立权限、明确确认提示和操作审计；首期不提供批量启停。
- [查看权限与状态权限配置错误] → 权限分离并分别覆盖接口、路由和按钮测试；默认仅授予平台超级管理员角色。
- [停用操作与租户请求并发] → 状态更新提交后，新请求由现有租户上下文检查拒绝；已进入事务的请求不强制中断，这是首期接受的最终一致性边界。

## Migration Plan

1. 新增 `PLATFORM_TENANT_VIEW`、`PLATFORM_TENANT_STATUS_EDIT` 权限并授予平台超级管理员角色，同时为 `operation_log` 增加 `detail_json`。
2. 发布平台租户查询、详情和状态 API；此时不影响现有团队侧流程。
3. 发布前端路由、菜单、列表、详情抽屉和启停交互。
4. 使用有查看权限、仅查看权限、无权限三类账号验证菜单、接口与按钮边界，并验证停用后可由平台重新启用。

回滚时先移除前端入口，再回滚后端接口。权限记录和审计字段可保留；不得删除已经产生的状态变更日志，也不得自动还原租户状态。
