## Context

生产深度审核当前按内容单元运行子 Agent，每个子 Run 同时加载全部选定维度，最终聚合 Run 只读取候选和历史问题。该结构可以控制长文本上下文，却会切断跨单元证据；当子 Run 返回空候选时，聚合 Run无法重新阅读原文。正式保存又把未匹配的历史问题直接复制为 `fixed`，使漏检转化为错误的修复结论。

线上使用 `gpt-5.6-terra`，经 `https://www.xiongxiongai.online/v1/chat/completions` 转发。重复稳定前缀测试中，第二次请求的 9,631 个输入 token 有 8,960 个被报告为缓存 token，说明可以通过稳定上下文前缀降低逐维审核成本。当前兼容适配器仅保留总 prompt token，没有保存该明细。

## Goals / Non-Goals

**Goals:**

- 让每个选定审核维度获得一次边界清晰、可独立重试的完整检查，提高问题召回率。
- 复用 GPT-5.6 Terra 的稳定剧本前缀缓存，并可观察缓存命中量、耗时和实际成本。
- 将高召回候选发现与高精度语义质检分开，所有裁决均可审计。
- 恢复跨集、跨维度的当前版本原文取证能力。
- 彻底隔离历史问题与新审核，消除历史答案提示和“本轮未发现即已修复”。
- 使用人工问题集持续量化各维度召回率和准确率。

**Non-Goals:**

- 不自动修改剧本，不替代人工最终裁决。
- 不要求供应商保存业务会话状态；服务端仍持有完整、可重放的审核状态。
- 不在本变更中重新定义前端审核工作台布局。
- 不保证每次请求百分之百命中供应商缓存；系统只保证构造稳定前缀并记录实际返回结果。

## Decisions

### 1. 采用逐维独立 Run，而非不断增长的单一对话

协调器为每个选定维度创建独立维度 Run。所有 Run 使用相同的固定前缀，动态后缀只描述当前维度及其检查清单。维度间只共享冻结原文和结构索引，不携带历史问题或其他维度的大段自然语言回答。

这样既能利用前缀缓存，又能避免早期结论对后续维度产生确认偏差。连续对话方案更接近人工交流，但上下文随轮次增长、失败恢复困难，故不采用。完全并行会增加首次缓存写入竞争；默认先完成缓存预热，再按受控并发执行维度 Run。

### 2. 缓存身份由不可变内容派生

缓存键由租户隔离标识、模型、剧本版本哈希、审核规则版本和工具合同版本派生。固定前缀按照“公共规则、工具定义、结构索引、冻结原文”的稳定顺序序列化，维度指令置于其后。任何固定内容变化都产生新键，避免复用错误上下文。

兼容适配器将缓存控制作为供应商能力处理：支持时发送稳定键和缓存选项；不支持时仍保持相同前缀并依赖自动缓存。是否命中只以响应 usage 为准，不能由请求成功推断。

### 3. 发现、语义裁决和综合报告分为三个阶段

发现阶段以召回率为目标，每个维度保存原始候选、精确证据位置和完整校验失败原因。机械无效候选不得静默丢弃，而应进入 `INVALID` 审计状态或触发一次结构纠正。

语义质检阶段逐条判断证据支持度、规则适用性、合理替代解释、严重度、建议有效性和重复关系，输出 `CONFIRMED`、`NEEDS_HUMAN_REVIEW`、`REJECTED` 或 `INSUFFICIENT_EVIDENCE`。质检不得物理删除原始候选。

综合阶段读取所有维度裁决以及按需原文，执行跨维度聚类和跨集复核。正式报告默认纳入 `CONFIRMED`，展示或附带 `NEEDS_HUMAN_REVIEW`，保留其他状态供审计。

### 4. 新审核与历史问题完全隔离

历史报告和历史问题继续持久化并可由用户主动查看，但任何新审核 Run 都不得读取它们。服务端保存新报告时不执行跨轮问题匹配，不修改旧问题状态，也不生成 `fixed`、`pending_recheck` 或 `uncertain`。每轮报告只表达对当前冻结版本的独立判断。

### 5. 零问题结果设置质量闸门

所有维度无候选或当前覆盖结果异常时，任务进入质量复核而不是直接完成。复核 Run 必须读取完整维度覆盖和必要的当前版本原文；不得用历史问题数量或内容判断异常。未通过时报告状态保持待复核且不能给出无条件满分。

### 6. 扩展 usage 数据但保持历史兼容

调用日志新增普通输入、缓存读取和缓存写入 token；现有 `prompt_tokens` 继续表示供应商报告的总输入量。计价按模型有效价格组件分别处理普通输入、缓存读取和缓存写入；供应商未返回明细时保持未知，而不是推断为零。既有记录不回填虚构的缓存数据。

### 7. 用人工问题集驱动验收

将人工发现的问题转换为脱敏、版本绑定的评测用例，记录期望维度、证据位置和可接受匹配范围。评测分别计算候选召回率、正式报告召回率、误报率、历史隔离正确率和缓存命中率。上线门槛以基准相对提升且历史内容对相同当前输入零影响为准。

## Risks / Trade-offs

- [逐维调用增加请求次数和输出费用] → 使用稳定前缀缓存、限制维度输出结构，并以线上 cache usage 实测监控总成本。
- [供应商网关接受但忽略缓存参数] → 以 `cached_tokens` 为唯一命中证据，并在缓存明细缺失时明确标记不可观测。
- [质检模型可能误删真实问题] → 保存全部原始候选，低置信否决进入人工复核，禁止不可逆删除。
- [完整剧本超过模型安全上下文] → 保留冻结单元读取工具与结构索引，维度 Run 按需分页读取，但综合 Run必须能检索任意相关片段。
- [逐维结果重复较多] → 只在综合阶段聚类，保留多证据和来源维度，不在发现阶段压制候选。
- [停止自动生命周期判断后无法自动声明问题已修复] → 保留旧报告只读查看，由人工比较不同轮次；新报告不修改任何历史状态。

## Migration Plan

1. 增加缓存 usage、维度 Run、候选裁决及质量状态字段和表，所有新增字段保持可空或有兼容默认值。
2. 扩展供应商适配器和日志链路，先只观测缓存数据，不改变现有审核编排。
3. 移除新审核对历史问题的读取、缓存身份依赖和自动生命周期匹配。
4. 在特性开关下启用逐维发现、语义质检和综合复核，对人工基准剧本影子运行。
5. 达到验收阈值后，将逐维流程设为 DEEP 默认；保留旧任务的只读展示和重试兼容。
6. 回滚时关闭新编排开关，旧协调器继续读取原任务结构；新增审计数据保留，不执行破坏性降级。

## Open Questions

- 首版受控并发默认值需要通过线上限流和缓存命中实验确定，建议从二开始。
- `NEEDS_HUMAN_REVIEW` 是否进入正式报告正文，还是单独显示在人工复核区，需要产品确认；设计默认单独展示但计入待处理数量。
- 人工三十余个问题清单需要固定到具体剧本版本，作为首个验收基准。

## Known Rollout Constraint

截至 2026-09-05，无法取得人工发现的三十余个问题及其对应的精确剧本版本。因此，
人工召回率、误报率和新旧流程质量对比暂时不可测，也不能据此声明达到质量上线门槛。
实现继续保留版本绑定评测能力，并使用合成用例验证匹配机制、历史隔离和边界条件；
合成用例不得伪装成人工质量基准，也不得送入审核模型。没有人工基准时，只允许进行
功能验证和受控影子运行，不能仅依据模型自评分将新流程设为默认。
