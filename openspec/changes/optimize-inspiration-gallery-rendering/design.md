## Context

Imported inspiration media is stored in the configured MinIO/S3 bucket and exposed through authenticated platform file endpoints. Gallery list items currently expose only the original media URL. The short-drama creation page can automatically expand from 8 to 24 cards before user scrolling, then asks the browser to load metadata from many original videos and decode full-resolution images at once. The storage implementation does not provide dynamic image transforms, so thumbnails must be generated by the application and stored as separate objects.

The change crosses import processing, database schema, object storage, authenticated media delivery, API response models, historical data, and frontend rendering. Existing external source URLs must remain transient and must not be reintroduced into persisted business data.

## Goals / Non-Goals

**Goals:**

- Store a compact visual thumbnail for each successfully imported image or video.
- Generate historical thumbnails from original objects already in the platform bucket.
- Keep original and thumbnail files behind authenticated platform endpoints.
- Make gallery cards request thumbnails only and load additional pages only after user scroll intent.
- Make stable media responses browser-cacheable without making them public.
- Isolate per-item thumbnail failures and make them observable and retryable.

**Non-Goals:**

- Add dynamic resizing to MinIO or expose direct public bucket URLs.
- Transcode or replace original inspiration media.
- Change gallery ordering, authorship, or external import API semantics.
- Build a general-purpose media processing platform.

## Decisions

### Persist dedicated thumbnail metadata

Add nullable `thumbnail_path`, `thumbnail_url`, `thumbnail_mime_type`, `thumbnail_file_size`, and `thumbnail_status` fields to `inspiration_creation`. Thumbnail objects use `inspiration/creations/{externalId}/thumbnail.jpg`; the API URL uses `/api/inspiration-creations/{id}/thumbnail`.

Dedicated columns make list queries cheap and allow historical rows to move through `PENDING`, `READY`, and `FAILED` independently of the original import status. Embedding these values in `detail_json` was rejected because list responses intentionally omit that large document and operational queries would be difficult.

### Generate a bounded JPEG preview in the application

Images are decoded, resized to fit within a configured maximum dimension without upscaling, and encoded as a supported compact image format. Videos are written to a temporary file and the existing JCodec dependency extracts an early representative frame, which is then normalized through the same image pipeline. Temporary files are removed in `finally` blocks.

Using the existing in-process JCodec dependency avoids a new system-level FFmpeg runtime and its deployment configuration. Using browser-generated previews was rejected because it would repeat work per client and could not backfill durable gallery thumbnails. Depending on MinIO URL transforms was rejected because the configured storage service exposes no such capability.

### Keep thumbnail generation behind a narrow service boundary

Introduce an inspiration thumbnail processor that accepts the original media stream plus MIME type and returns encoded thumbnail bytes and metadata. Import orchestration uploads the original first, invokes the processor, uploads the thumbnail, then marks the record `IMPORTED` with thumbnail status `READY`. A thumbnail failure records `FAILED` and its error while preserving the successfully imported original; the record remains available with a controlled fallback preview.

This isolates external process execution from import parsing and makes image and video behavior unit-testable. Folding FFmpeg execution into the controller or importer was rejected because it couples transport, persistence, and process lifecycle.

### Backfill from stored originals

A resumable maintenance service selects imported records whose thumbnail is not `READY`, reads each original through `ObjectStorageService`, generates and uploads the thumbnail, and updates only that record. It processes a bounded batch and isolates failures per item. Re-running it is idempotent because `READY` records are skipped and the deterministic thumbnail object key can be overwritten safely.

A Flyway migration only adds columns and indexes; it does not access object storage or run FFmpeg. Performing media work during schema migration was rejected because it would make startup and rollback dependent on large remote objects and host binaries.

### Return both protected URLs with an explicit fallback

List and detail items add `thumbnailUrl`. When thumbnail status is `READY`, the value is the local thumbnail endpoint. Until backfill succeeds, the API may return `null`; the frontend displays a lightweight type placeholder rather than automatically loading the original video. Opening the detail modal continues to request the original URL.

The thumbnail and original endpoints use private browser cache control with a finite max age. Authentication remains required on cache misses, and no presigned or external source URL is exposed.

### Gate pagination and media loading on visibility

The first gallery request remains 8 records. Infinite scrolling is enabled only after an actual downward scroll event, preventing layout-driven observer callbacks from preloading subsequent pages. Thumbnail images use native lazy loading and asynchronous decoding; cards outside the proximity threshold do not receive a thumbnail `src` until observed. Environments without `IntersectionObserver` load the thumbnail directly as a compatibility fallback.

An explicit “load more” button was considered but rejected because the existing infinite-scroll interaction should remain unchanged.

## Risks / Trade-offs

- [Some video codecs cannot be decoded by JCodec] → Record a concise per-item failure, preserve the original object, and allow retry after adding a compatible extractor if operational data requires it.
- [Historical backfill consumes CPU and object-storage bandwidth] → Run bounded batches, skip `READY` rows, and keep the process resumable.
- [Some source images or videos cannot be decoded] → Preserve the original imported record, set thumbnail status `FAILED`, and render a type placeholder instead of fetching the original in the grid.
- [JPEG writer support varies by JVM distribution] → Verify writer availability during processing and record a clear per-item failure; tests cover the configured runtime support.
- [Private browser caching may retain media until expiry after authorization changes] → Use a moderate finite max age rather than immutable/public caching; authorization is still checked on cache misses.
- [Scroll gating may delay pagination for keyboard or programmatic navigation] → Treat document scrolling from any input method as intent and retain observer-based boundary detection.

## Migration Plan

1. Deploy the additive schema migration and backend support for nullable thumbnail fields and endpoints.
2. Deploy import-time generation and the bounded backfill operation.
3. Run backfill in batches and monitor `thumbnail_status` failures without blocking existing original media access.
4. Deploy the frontend thumbnail rendering and pagination gate; records without ready thumbnails render placeholders.
5. Re-run failed backfill rows after resolving decode errors.

Rollback keeps the additive columns and stored thumbnail objects. The frontend can revert to original URLs, and older backend versions ignore the additional columns. Object cleanup is deferred until the optimized path is permanently retired.

## Open Questions

None. The implementation will use the existing JCodec frame extractor, bounded JPEG thumbnails, authenticated local URLs, and an explicit batch backfill entry point consistent with existing operational conventions.
