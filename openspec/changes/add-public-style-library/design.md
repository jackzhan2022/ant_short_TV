## Context

项目已经有图片生成任务、项目视觉风格的规划文档和 AI 服务配置能力，但当前已实现的图片生产表单只有一个自由文本 `style` 字段。用户提供的风格数据包含 139 条平台公共风格，每条有来源 ID、名称、描述、公开标记、参考图 URL、图片尺寸和角色信息；这些数据更适合作为平台级公共参考库，而不是立即复制到每个项目。

本变更只建立只读浏览能力。公共风格库可以帮助创作者在进入项目生产前浏览视觉方向，后续再通过独立变更扩展为“复制到项目视觉风格”或“图片生成任务选择风格”。

## Goals / Non-Goals

**Goals:**

- 将用户提供的公共风格数据导入后端 `style_library` 表，并将参考图转存到平台对象桶。
- 提供只读 API，支持按分类和关键词查询公共风格。
- 在前端新增 `风格库` 一级菜单，以响应式网格卡片展示风格参考图、名称、分类和描述。
- 保留外部来源 ID、原始图片 URL、对象存储路径和图片元数据，方便后续追踪导入来源、去重和重新转存。
- 保持实现边界轻量，不影响现有图片生成、项目设置或素材库流程。

**Non-Goals:**

- 不实现风格新增、编辑、删除、启停或后台管理。
- 不实现团队/项目私有风格，不新增项目视觉风格配置。
- 不把公共风格应用到图片生成任务，不修改 `ai_image_task.style` 的生成逻辑。
- 不新增复杂权限模型；第一版面向已登录用户只读可见。

## Decisions

### 1. 使用后端表和 seed/import，而不是前端静态 JSON

新增 `style_library` 表保存公共风格记录，前端通过 API 查询。字段包括自增主键、`external_id`、`name`、`category`、`description`、`source_image_url`、`storage_path`、`image_url`、`image_width`、`image_height`、`is_public`、`sort_order`、时间字段。

备选方案是把 139 条数据放到前端静态 JSON。静态 JSON 实现更快，但后续无法自然支持服务端搜索、去重、权限和项目引用，因此不采用。

### 2. 参考图转存到平台对象桶

导入时从用户提供的原始图片 URL 拉取参考图，上传到平台对象桶的公共风格库路径，建议路径为 `style-library/public/{externalId}/cover.{ext}`。`source_image_url` 保存原始 URL，`storage_path` 保存对象桶内部路径，`image_url` 保存前端展示可访问地址。风格库图片不写入 `material` 表，也不使用 `/materials/{tenantId}/{projectId}/...` 项目素材路径。

备选方案是直接使用原始外链。该方案实现更轻，但公共库可用性受外部 URL 生命周期影响，因此不采用。另一个备选方案是保存为项目素材，但公共风格不属于某个团队或项目，会污染项目素材权限和清理策略，因此不采用。

### 3. 从名称前缀推导分类

导入时根据名称中的第一个 `-` 或 `－` 提取分类，例如 `3D风格-高清真实渲染` 归类为 `3D风格`；没有明确分隔符的记录归为 `未分组`。前端分类筛选使用后端返回的分类值，不在浏览器重复推导。

备选方案是保留原始名称不分类。该方案会让 139 条网格缺少浏览锚点，用户难以扫描，因此不采用。

### 4. API 保持只读和扁平

第一版提供 `GET /api/style-library`，支持 `keyword` 和 `category` 查询参数，返回按 `sortOrder`、`id` 排序的扁平列表。响应只包含浏览所需字段，不暴露导入角色、创建人等来源细节。

备选方案是提供分页和管理接口。当前数据量只有 139 条，网格浏览一次返回可接受；管理动作和分页可以后续在数据量扩大时追加。

### 5. 前端页面使用 Pro/antd 现有布局，但以网格卡片为主

新增页面放在 `frontend/src/pages/style-library`，路由为 `/style-library`，菜单名为 `style-library`。页面提供搜索框、分类筛选和响应式网格。卡片展示参考图、名称、分类 Tag 和描述；点击图片可用 antd 图片预览查看大图。

页面不出现“应用”“编辑”“复制到项目”等动作，避免用户误以为风格已经接入生产流程。

### 6. 权限先复用登录态

路由 access 使用一个轻量的 `canViewStyleLibrary`，只要求 `currentUser` 存在。后端接口同样只要求通过现有认证上下文，不新增 `STYLE_LIBRARY:VIEW` 权限。

备选方案是新增 RBAC 权限。公共风格库是只读基础资源，第一版新增 RBAC 会增加迁移和角色配置成本；等出现管理或团队隔离需求时再引入更合适。

## Risks / Trade-offs

- [远程图片下载失败] -> 导入任务记录失败来源并跳过或保留待重试状态；实现阶段应支持重跑单条转存而不重复创建风格记录。
- [对象桶展示 URL 失效或权限错误] -> 使用平台公共资产访问策略或受控公开读 URL，前端保留图片加载失败占位。
- [名称前缀分类不完美] -> 将无前缀记录归为 `未分组`，不阻塞浏览；后续可增加人工分类字段迁移。
- [一次返回全部数据] -> 当前 139 条数据量较小，可接受；如果公共库增长到数千条，再引入分页和服务端排序。
- [描述较长影响卡片高度] -> 前端卡片描述做行数限制，详情可通过悬浮/预览或后续抽屉扩展。
- [只读库和项目风格概念混淆] -> 页面文案和按钮保持浏览语义，不提供生产动作。

## Migration Plan

1. 发布 Flyway 迁移，创建 `style_library` 表并导入 139 条公共风格元数据。
2. 执行参考图转存，将原始图片拉取并上传到平台对象桶公共风格路径，回写 `storage_path` 和 `image_url`。
3. 发布后端查询服务和 `GET /api/style-library` 接口。
4. 发布前端菜单、服务请求和网格浏览页。
5. 回滚时隐藏前端菜单并停止调用接口；保留数据表和对象桶文件不影响现有业务。

## Open Questions

- 是否需要把 `created_by`、`roles` 等来源字段完整保留为 JSON 元数据，目前设计只保留浏览、转存和去重所需字段。
- 第一版是否需要多语言风格名称/描述，目前按用户提供的中文数据展示。
