# V1\.0\-02 技术开发需求文档

## RBAC 角色与权限体系

所属产品：短剧制作 SaaS 平台
版本：V1\.0\-02
前置版本：V1\.0\-01 账号与创作团队基础体系
核心目标：建立基于“创作团队”的 RBAC 权限体系

## 1\. 文档概述

### 1\.1 建设背景

V1\.0\-01 已经完成 SaaS 基础身份体系：

```Plaintext
User
  ↓
TenantMember
  ↓
Tenant（创作团队）
```

并支持：

- 用户自主注册

- 创建创作团队

- 加入多个创作团队

- 团队邀请

- 团队成员管理

- 多团队切换

- 当前团队上下文

V1\.0\-02 在此基础上解决：

**“用户进入一个创作团队以后，能够做什么？”**

因此本版本建立：

```Plaintext
用户
 ↓
创作团队成员
 ↓
角色
 ↓
权限
 ↓
菜单 / 页面 / 按钮 / API
```

## 2\. 二、核心设计原则

### 2\.1 权限必须绑定团队

这是整个系统最重要的原则。

不能设计：

```Plaintext
User
 ↓
Role
```

而必须：

```Plaintext
User
 ↓
TenantMember
 ↓
Role
 ↓
Permission
```

例如：

张三
│
├── 星河影视
│ └── Owner
│ └── 全部权限
│
└── 蓝海传媒
└── 编剧
└── 剧本相关权限

张三切换团队以后，权限必须跟着团队变化。

## 3\. 三、V1\.0\-02建设目标

本版本完成以下能力：

### 3\.1 角色管理

支持：

- 创建角色

- 编辑角色

- 删除角色

- 查看角色

- 角色状态

- 角色描述

### 3\.2 权限管理

建立统一权限模型：

- 菜单权限

- 页面权限

- API权限

- 按钮/操作权限

### 3\.3 成员角色分配

支持：

- 给成员分配角色

- 修改成员角色

- 移除角色

- 查看成员权限

### 3\.4 默认角色

系统提供基础角色：

- Owner

- Admin

- Member

但需要特别注意：

V1\.0\-01中的 Owner / Member 是成员身份，不等同于完整 RBAC 角色。

V1\.0\-02开始，可以逐步统一到 RBAC 模型。

## 4\. 四、本版本不做什么

为了避免第一版 RBAC 过度复杂，以下能力暂不实现：

**暂不实现**

- 数据行级权限

- 字段级权限

- ABAC

- 多层级复杂角色继承

- 权限表达式

- 项目级自定义权限

- 临时权限

- 时间权限

- IP权限

- 审批流权限

- SSO

- 企业级组织权限

这些属于后续高级权限体系。

## 5\. 五、核心权限模型

V1\.0\-02采用标准 RBAC：

```Plaintext
User
 ↓
TenantMember
 ↓
Role
 ↓
Permission
```

但为了支持一个成员拥有多个角色，建议最终设计为：

```Plaintext
User
 ↓
TenantMember
 ↓
MemberRole
 ↓
Role
 ↓
RolePermission
 ↓
Permission
```

即：

> 一个用户
↓
一个团队成员身份
↓
多个角色
↓
多个权限

## 6\. 六、为什么建议一个成员支持多个角色

例如张三：

```Plaintext
星河影视
│
├── 制片人
└── 项目管理员
```

那么张三获得：

- 制片权限

    - 

- 项目管理权限

如果限制一个成员只能有一个角色，后续很容易出现：

> “为了满足某个人的特殊职责，需要创建大量重复角色。”

因此建议：

**Member 与 Role 使用多对多关系。**

## 7\. 七、角色模型

核心关系：

```Plaintext
Tenant
  │
  └── Role
       │
       └── Permission
```

角色属于团队。

例如：

```Plaintext
星河影视
│
├── Owner
├── 管理员
├── 制片人
├── 编剧
├── 导演
└── 后期
```

而：

```Plaintext
蓝海传媒
│
├── Owner
├── 管理员
└── 编剧
```

两个团队之间角色完全隔离。

## 8\. 八、角色分类

建议角色增加：

`role_type`

分为：

**SYSTEM**
系统预置角色。

例如：

- Owner

- Admin

- Member

**CUSTOM**
团队自定义角色。

例如：

- 制片人

- 编剧

- 导演

- 剪辑

- 美术

- 财务

## 9\. 九、系统角色与自定义角色

### 9\.1 系统角色

平台定义。

特点：

- 不允许删除

- 部分基础属性不允许修改

- 权限由系统维护

例如：

- Owner

### 9\.2 自定义角色

团队Owner/Admin创建。

例如：

- 短剧编剧

- AI编剧

- 项目制片

- 后期剪辑

团队可以：

- 修改

- 停用

- 删除

## 10\. 十、角色数据模型

建议：

**role**

|字段|类型|说明|
|---|---|---|
|id|bigint|角色ID|
|tenant\_id|bigint|所属团队|
|code|varchar|角色编码|
|name|varchar|角色名称|
|description|varchar|角色描述|
|role\_type|varchar|SYSTEM/CUSTOM|
|status|tinyint|状态|
|is\_default|boolean|是否默认角色|
|created\_by|bigint|创建人|
|created\_at|datetime|创建时间|
|updated\_at|datetime|更新时间|
|deleted\_at|datetime|删除时间|

## 11\. 十一、角色唯一性

同一个团队：

`tenant_id + role_code`

必须唯一。

例如：

`星河影视 + SCRIPT_WRITER`

只能存在一个。

但：

`星河影视 + 编剧`
`蓝海传媒 + 编剧`

可以同时存在。

**资源 \+ 操作**

- PROJECT:EDIT

- PROJECT:DELETE

剧本：

- SCRIPT:VIEW

- SCRIPT:CREATE

- SCRIPT:EDIT

- SCRIPT:DELETE

- MEMBER:VIEW

- MEMBER:REMOVE

## 14\. 十四、权限类型

虽然底层统一使用 Permission，但需要区分权限作用范围。

建议：

- MENU

- PAGE

- BUTTON

- API

例如：

菜单

- PROJECT:MENU

页面

- PROJECT:VIEW

按钮

- PROJECT:CREATE

- PROJECT:DELETE

API

- PROJECT:API:CREATE

不过这里建议进一步优化：

不要让前端菜单权限和后端API权限成为两套独立体系。

推荐：

> Permission
├── code
├── type

└── action

## 19\. 十九、Owner权限

Owner属于特殊角色。

建议：

**Owner**

拥有当前团队全部权限。

但是不要简单地在每一个API里面写：

```Java
if (user == owner) {
    return true;
}
```

推荐统一进入权限服务：

`PermissionService`

判断：

```Plaintext
isOwner()
    ↓
true
    ↓
拥有全部Tenant权限
```

这样后续方便统一维护。

## 20\. 二十、默认角色

V1\.0\-02建议系统提供：

- Owner

- 管理员 Admin

- 普通成员 Member

但是这里需要和 V1\.0\-01 衔接。

**团队创建**

V1\.0\-01：

```Plaintext
Tenant
+
TenantMember(OWNER)
```

**RBAC初始化**

V1\.0\-02：

> 当团队第一次进入RBAC体系时：

- Owner

- Admin

- Member

> 建立默认角色。

这样符合你刚才确定的：

> 创建团队时不自动创建角色。

即：

V1\.0\-01不创建角色；V1\.0\-02首次启用权限体系时进行角色初始化。

## 25\. 二十五、角色删除

自定义角色可以删除。

但存在成员使用时：

**不建议直接删除。**

提示：

> 当前角色已分配给 X 名成员，请先完成角色调整。

建议第一版：

> 存在成员
↓
禁止删除

或者：

> 停用角色

优先推荐后者。

## 26\. 二十六、角色停用

角色状态：

- ACTIVE

- DISABLED

角色停用后：

1. 新成员不能分配

2. 已分配成员失去该角色权限

3. 历史数据保留

## 30\. 三十、权限缓存

考虑到每次请求查询完整权限链路成本较高，建议V1\.0\-02增加缓存。

例如：

Redis

Key：
`permission:{tenantId}:{memberId}`

Value：

```JSON
[
  "PROJECT:VIEW",
  "PROJECT:CREATE",
  "SCRIPT:VIEW",
  "SCRIPT:EDIT"
]
```

## 31\. 三十一、权限缓存失效

以下操作必须清理缓存：

- 角色权限修改

- 成员角色修改

- 角色删除

- 角色停用

- 成员移除

- Owner转让

例如：

```Plaintext
修改编剧角色
 ↓
删除相关Member权限缓存
 ↓
下一次请求重新计算
```

## 32\. 三十二、后端权限注解

建议提供统一注解：

`@RequirePermission("PROJECT:CREATE")`

例如：

```Java
@PostMapping("/projects")
@RequirePermission("PROJECT:CREATE")
public Project createProject() {
}
```

由统一拦截器/AOP处理。

## 33\. 三十三、前端权限

前端不能仅通过隐藏按钮实现安全控制。

例如：

`[删除项目]`

即使前端隐藏：

`POST /api/projects/delete`

后端仍然必须验证：

`PROJECT:DELETE`

原则：

> **前端负责体验，后端负责安全。**

## 34\. 三十四、菜单权限

登录以后前端获取当前用户可访问菜单。

接口：

`GET /api/auth/permissions`

返回：

```JSON
{
  "menus": [
    "PROJECT",
    "SCRIPT"
  ],
  "permissions": [
    "PROJECT:VIEW",
    "PROJECT:CREATE",
    "SCRIPT:VIEW",
    "SCRIPT:EDIT"
  ]
}
```

前端根据权限：

- 菜单显示

- 按钮显示

- 页面操作

## 35\. 三十五、API权限

后端API必须单独验证。

例如：

`GET /projects`

需要：`PROJECT:VIEW`

而：

`POST /projects`

需要：`PROJECT:CREATE`

## 36\. 三十六、数据权限暂不实现

V1\.0\-02只解决：

**功能权限**

暂不解决：

**数据权限**

例如：

> 编剧A只能看自己剧本
编剧B只能看自己剧本
制片人可以看全部项目

这种属于数据权限。

V1\.0\-02先不做。

## 38\. 三十八、超级管理员

平台超级管理员：

`PlatformAdmin`

和租户Owner是两个体系。

```Plaintext
平台管理员
      │
      ↓
SaaS Platform
      │
      ├── Tenant A
      ├── Tenant B
      └── Tenant C
```

平台管理员权限不应该通过普通Tenant RBAC实现。

建议单独：

- PlatformUser

- PlatformRole

- PlatformPermission

V1\.0\-02可以只预留，不做完整平台RBAC。

**一个特别重要的架构结论**

V1\.0\-02不要把“组织架构”和“RBAC”强绑定。

应该允许：

```Plaintext
Tenant
│
├── 成员
│    └── Role
│
└── 后续再建立 Organization
```

因为未来你的短剧团队可能非常灵活：

```Plaintext

├── 编剧
├── 导演
├── 制片
├── AI创作
├── 剪辑
└── 外部合作人员
```

这些首先是权限角色，不一定是组织部门。

等到后面真正出现：

> “编剧中心 → 剧本组 → A组”

这种管理需求时，再引入 Organization，会比现在把两套模型揉在一起更稳。
