**文档版本：** V1.0-03

# 一、需求概述

## 1.1 项目背景

短剧制作平台采用多租户 SaaS 架构。

V1.0-01 已解决：

- 用户账号体系
- 用户登录
- 租户体系
- 用户与租户关系
- 用户加入多个团队/租户
- 租户切换
- 多租户数据隔离

V1.0-02 已解决：

- RBAC 权限模型
- 组织/部门
- 系统角色
- 菜单权限
- 页面权限
- 按钮权限
- API 权限
- 基础数据权限

V1.0-03 在此基础上进一步解决：

> **一个租户内部如何进行组织管理、项目管理，以及不同成员如何访问不同项目。**

短剧制作天然具有项目制特点。

例如一个创作团队可能同时制作：

- 《霸总归来》
- 《重生后我成了首富》
- 《离婚后她成了顶流》
- 《八零年代小娇妻》

同一个用户可能参与多个项目，但在不同项目中承担的职责不同。

因此不能仅依赖“租户 + 系统角色”控制权限，需要增加：

> **组织 → 项目 → 项目成员 → 项目角色 → 项目数据范围**

形成完整的项目级权限控制体系。

# 四、总体权限模型

V1.0-03最终形成以下权限结构：

```text
平台
 └── 租户
      ├── 用户
      │
      ├── 组织
      │    ├── 一级组织
      │    │    ├── 二级组织
      │    │    └── ...
      │
      ├── 系统角色
      │
      └── 项目
           ├── 项目A
           │    ├── 项目成员
           │    ├── 项目角色
           │    └── 项目权限
           │
           ├── 项目B
           │    ├── 项目成员
           │    ├── 项目角色
           │    └── 项目权限
           │
           └── 项目C
```

权限判断原则：

```text
用户
 ↓
是否属于当前租户
 ↓
租户级权限
 ↓
是否属于当前项目
 ↓
项目角色
 ↓
项目功能权限
 ↓
项目数据范围
 ↓
最终是否允许访问
```

# 五、组织架构模块

## 5.1 组织架构目标

支持一个租户建立自己的内部组织结构。

例如：

```text
星河短剧
├── 制作中心
│   ├── 编剧组
│   ├── 导演组
│   └── 制片组
│
├── 美术中心
│   ├── 原画组
│   ├── 设计组
│   └── 后期组
│
└── 运营中心
    ├── 投放组
    └── 运营组
```

---

## 5.2 组织层级

V1.0-03支持最多5级组织。

例如：

```text
租户
 ↓
中心
 ↓
部门
 ↓
小组
 ↓
项目组
```

系统应限制：

```text
level <= 5
```

超过5级禁止创建。

## 5.5 删除规则

存在以下情况时禁止删除：

### 1. 存在子组织

```text
当前组织存在下级组织
→ 禁止删除
```

### 2. 存在成员

如果组织下存在成员，需要先处理成员归属。

### 3. 存在项目关联

如果组织仍作为项目归属组织使用，应禁止直接物理删除。

采用：

> 逻辑删除。

# 九、项目状态

V1.0-03默认提供：

```text
未开始
进行中
已暂停
已完成
已归档
```

状态流转：

```text
未开始
 ↓
进行中
 ↓
已完成
 ↓
已归档
```

允许：

```text
进行中 → 已暂停
已暂停 → 进行中
```

已归档项目原则上只允许查看，不允许进行普通业务操作。

# 十、项目负责人

每个项目必须存在一个负责人。

项目负责人：

- 可以查看项目
- 可以管理项目成员
- 可以查看项目基本信息
- 可以执行项目级管理操作

但项目负责人权限不能绕过系统RBAC。

即：

> “项目负责人”是项目角色，不是超级管理员。

---

# 十一、项目成员体系

## 11.1 多项目成员

一个用户可以加入多个项目。

例如：

```text
张三

项目A → 编剧
项目B → 导演
项目C → 项目负责人
```

因此项目成员关系必须独立于用户表。

# 十三、项目角色与系统角色的区别

### 系统角色

负责：

```text
租户管理
组织管理
用户管理
角色管理
权限管理
系统配置
```

### 项目角色

负责：

```text
项目访问
项目业务权限
项目成员管理
项目数据访问
```

二者不能混淆。

例如：

```text
用户A
系统角色：普通成员
项目A角色：项目负责人
项目B角色：编剧
```

---

# 十四、项目角色权限模型

项目角色绑定V1.0-02已经建立的权限资源。

例如：

```text
项目负责人
├── project:view
├── project:update
├── project:member:view
├── project:member:add
├── project:member:remove
└── project:member:update

编剧
├── project:view
└── project:content:view
```

V1.0-03暂不实现剧本等具体业务权限，但需要预留权限资源模型。

---

# 十五、项目数据范围

项目权限至少支持以下范围：

```text
ALL
ORGANIZATION
PROJECT
```

### ALL

可以访问租户范围内允许的数据。

### ORGANIZATION

只能访问所属组织的数据。

### PROJECT

只能访问当前项目的数据。

---

# 十六、权限判断

后端每次访问项目数据必须执行：

```text
1. 校验用户身份
2. 校验tenant_id
3. 校验租户状态
4. 校验用户是否属于租户
5. 校验项目是否属于租户
6. 校验用户是否具有项目访问资格
7. 校验项目角色
8. 校验功能权限
9. 校验数据范围
10. 执行业务操作
```

任何一步失败均不得继续执行。

---

# 十七、项目访问控制

用户进入项目时：

```text
GET /api/projects/{projectId}
```

后端必须验证：

```text
currentUser.tenantId == project.tenantId
```

以及：

```text
user ∈ project_member
```

或者：

```text
user具有租户级项目管理权限
```

否则：

```text
403 FORBIDDEN
```

---

# 十八、租户隔离要求

所有核心业务表必须包含：

```text
tenant_id
```

包括：

- organization
- organization_member
- project
- project_member
- project_role
- project_role_permission
- project_operation_log

任何查询不得只通过：

```text
id
```

查询。

必须优先使用：

```sql
WHERE tenant_id = currentTenantId
AND id = xxx
```

防止越权访问。

# 二十三、项目成员变更规则

项目成员被移除后：

```text
立即失去项目访问权限
```

但历史数据不能删除。

例如：

```text
张三曾参与项目A
↓
张三被移除
↓
历史操作日志仍然保留
```

---

# 二十四、项目归档

项目归档后：

- 项目可以查看
- 项目成员可以查看
- 普通业务写操作禁止
- 项目成员管理禁止
- 项目角色调整禁止

只有具备项目管理权限的用户才能取消归档。

```text
项目权限
组织树
```

缓存Key必须包含tenant_id。

例如：

```text
tenant:{tenantId}:user:{userId}:permissions
```

禁止使用：

```text
user:{userId}:permissions
```

避免多租户缓存污染。

# 三十二、并发控制

项目成员管理必须考虑并发。

例如：

```text
管理员A移除张三
管理员B同时修改张三角色
```

系统需要避免出现最终状态不一致。

建议：

- 数据库事务
- 乐观锁
- updated_at/version校验
- 唯一约束


以及：


## 35.2 IDOR防护

不能因为知道：

```text

```

必须进行：

```text
tenant + permission + project membership
```

三重校验。

# 三十六、前后端权限一致性

前端权限：

```text
控制菜单
控制按钮
控制页面
```

后端权限：

```text
真正安全边界
```

前端隐藏按钮不能作为安全机制。

例如：

```text
前端隐藏“删除项目”
```

但用户直接调用：

```http
DELETE /api/projects/10001
```

后端仍必须进行权限验证。

# 四十六、版本边界总结

V1.0整体建议形成：

```text
V1.0-01
统一身份与租户
        ↓
V1.0-02
RBAC权限体系
        ↓
V1.0-03
组织 + 项目 + 项目权限
        ↓
V1.0-04
短剧业务核心能力
```

其中V1.0-03的核心不是做短剧业务，而是建立：

> **“一个租户如何管理多个创作组织、多个短剧项目，以及一个用户如何在不同项目中拥有不同权限”的基础平台能力。**

最终权限模型：

```text
平台
 ↓
租户
 ↓
用户
 ↓
组织
 ↓
项目
 ↓
项目成员
 ↓
项目角色
 ↓
功能权限
 ↓
数据权限
```

这套模型完成后，后续新增“剧本、剧集、角色、场景、分镜、素材、任务、AI”等业务模块时，都可以直接复用 `tenant_id + project_id + user_id + permission` 这一套权限上下文，而不需要重新设计权限体系。
