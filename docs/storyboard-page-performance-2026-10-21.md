## 已确认的主要问题

### 1. 分镜接口主要耗在数据库读取

线上 `/opt/antv/shared/logs/backend.log` 的请求级统计：

| 日志时间 | HTTP 耗时 ms | SQL 次数 | SQL 累计耗时 ms |
| --- | ---: | ---: | ---: |
| 14:42:12.004 | 26107 | 13 | 26098 |
| 14:44:22.532 | 9743 | 13 | 9734 |
| 14:46:45.452 | 18540 | 13 | 18530 |
| 14:47:33.219 | 6583 | 13 | 6574 |

慢请求期间，JVM HTTP 线程采样出现 MySQL 驱动读取结果、SSL Socket 等待栈。数据库调用时间包含驱动等待与结果读取，不能全部解释为 SQL 在数据库内执行的时间，也不能仅凭这些数据判定缺少某个索引。

### 2. 最新批次查询逐集读取完整分镜 JSON 统计告警

本地对应实现 `StoryboardBatchService.response()` 遍历批次条目；`itemResponse()` 对每项单独查询执行任务，成功任务继续调用 `warningCount()` 查询该集完整 `shot_plan_json`，在 Java 内解析告警。

只读 SQL 核实：项目最新批次 85 项，全部执行成功。按该实现，业务查询至少包括批次 1 次、条目列表 1 次、任务 85 次、告警 85 次，即 172 次；此数为源码推导，不是该接口的线上 SQL 计数。

复测与告警统计等价的第一集查询：返回 33 行、1,117,252 字节，客户端总耗时 1,246.3 ms。该项目当前有效分镜共 851 条，`shot_plan_json` 合计 10,243,091 字节。即使页面只展示当前一集，批次状态接口仍会逐集扫描这些大 JSON。四次刷新批次接口稳定约 25～26 秒。

### 3. 页面读取了较多大字段，JSON 响应未压缩

分镜接口单次响应正文 1,110,682 字节，首屏 20 条分镜的数据库字段包含：`shot_plan_json` 678,637 字节、`prompt_document_json` 124,580 字节；还会读取全部剧集概要，85 份概要 JSON 共 115,785 字节。分镜接口为获取剧本 ID 还调用完整剧本读取。

项目详情每次正文 291,592 字节，项目初始剧本字段本身为 271,312 字节；素材摘要正文 323,749 字节。

浏览器响应没有 `Content-Encoding`，传输体积与解码体积基本相等。服务器 antv 站点没有配置 JSON 压缩；全局只有 `gzip on`，包含 `application/json` 的 `gzip_types` 行为注释。压缩可以减少传输，但不能解决前述数据库等待。

### 4. 父页面与分镜子页面重复读取项目详情

`frontend/src/pages/projects/production-workbench/index.tsx:57` 和 `storyboard.tsx:1854` 各调用一次 `queryProject(projectId)`。网络记录与代码一致，每次刷新重复读取约 292 KB 的项目详情。

### 5. 其他容量信号

测试时服务器 CPU 大多空闲；8 GB 内存仅约 363 MB available，1 GB swap 已用满。但 `vmstat` 采样期间 `si/so` 为 0，没有观察到持续换页，因此内存紧张属于容量风险，不能据此认定是此次 26 秒等待的直接原因。没有在近期日志中观察到所筛查的 Redis 超时或 Hikari 线程饥饿提示。

## 建议优化顺序

1. 优先消除批次接口的逐集查询：批量读取任务状态；数据库聚合告警数量或在分镜生成完成时记录告警统计，避免每次访问重读所有分镜 JSON。保留租户、项目及权限边界。
2. 分镜首屏按使用范围读取字段：导航只取导航字段；完整剧集概要、完整 shot plan 等放到实际需要的详情接口。避免为拿剧本 ID 读取正文。
3. 父子页面共用项目状态，去掉重复详情请求；项目元数据与完整原文按需要分别获取。
4. 为 JSON 响应配置 gzip，再对比传输体积和加载时间。该项应在上述数据库读取优化之外单独验证。
5. 后续再根据单条 SQL 耗时与 EXPLAIN 决定索引调整，并检查主机内存容量。不要直接加并发、扩大连接池或把所有内容塞入缓存来掩盖问题。

## 证据与限制

汇总数据：`outputs/storyboard-page-performance-20261021.json`。只保留耗时、字节数和聚合计数，没有保存 Cookie、密码、剧本或提示词正文。

SQL CLI 测量包含新连接与只读事务开销。浏览器 TTFB 包含用户到服务器的网络链路；服务器日志能够独立证明主要数据库等待。每个模型与配置接口尚未做单独 SQL 定位，不能将这些接口全部归结为相同 SQL。

本次交付为测试与原因定位，没有应用修复或变更线上环境。

## 补充：数据库计算与结果传输对照

在应用服务器上，使用相同租户、项目、剧集、执行任务条件，交替查询同一批 33 条分镜三次。均使用只读事务。

| 返回内容 | 结果字节数 | 三次客户端耗时 ms |
| --- | ---: | --- |
| 数量与 JSON 总字节数 | 11 | 66.26 / 61.26 / 61.72 |
| 完整 shot_plan_json | 1,116,505 | 1401.60 / 3233.88 / 3285.70 |

完整 JSON 字段自身合计 1,116,472 字节。客户端耗时包含连接与事务开销；采用 `--raw` 输出，字节数与上文首次 CLI 转义输出的字节数略有区别。只记录字节数，不保存正文。

对完整 JSON 查询执行 `EXPLAIN ANALYZE`，根节点实际时间为 `0.0652..0.611 ms`，返回 33 行。执行计划使用 `idx_ai_call_log_execution`、`idx_storyboard_active_episode_order`、`uk_ai_workflow_agent_run_step`。这是热缓存条件下的样本，说明该样本的查找执行很快；不能推广为所有接口、所有查询都没有执行开销。EXPLAIN ANALYZE 不向应用返回全部 JSON，不能反映完整大结果回传时间。

进一步核对当前应用进程的 MYSQL_URL 与 shared/env 一致，并将 IPv4-mapped IPv6 地址规范化后核对 7 条数据库连接，全部指向该配置的公网地址。未输出连接凭据或具体数据库地址。

结论：至少对这条单集查询，主要耗时在读取并回传大结果，而不是查找 33 行本身。应用又在最新批次查询中逐集重复取完整 JSON，将传输和往返成本放大。应优先减少返回字段、批量聚合告警，并核实应用与数据库能否通过同地域同 VPC 的内网地址连接；是否存在公网带宽限制或丢包，仍需单独网络与云侧指标验证。
