# 充值中心积分明细合并设计

## 背景

充值中心当前单独展示“权益发放记录”，团队设置页则展示团队积分汇总和积分流水。商业套餐发放积分时已经同时写入权益发放记录与积分账本，因此直接拼接两套记录会造成重复。

## 目标

- 充值中心以积分账本作为唯一明细来源。
- 用积分变化类型区分权益发放、积分消耗、预扣、释放、退款及历史手工调整。
- 团队设置页不再展示或请求任何积分汇总与积分明细。
- 保留充值中心顶部的团队积分余额。

## 非目标

- 不改变支付、订阅或权益发放状态机。
- 不修改积分余额计算与记账规则。
- 不删除商业权益发放记录表或其后台查询接口；它仍可供商业域审计使用。
- 不增加积分明细筛选、分页交互或导出功能。

## 方案

### 单一数据来源

充值中心继续通过团队积分账户接口读取余额，并通过团队积分流水接口读取明细。页面不再请求商业权益发放记录，也不再渲染独立的“权益发放记录”表。

商业权益积分在发放时已经进入积分账本，所以统一列表不会遗漏已发放积分，也不会产生重复行。

### 积分变化类型

积分流水接口应为商业套餐产生的发放记录返回明确的权益发放类型，同时保留历史手工发放的既有类型。前端将接口类型转换为用户可读文案：

| 流水类型 | 展示文案 |
| --- | --- |
| `ENTITLEMENT_GRANT` | 权益发放 |
| `ADJUST_GRANT` | 手动增加 |
| `RESERVE` | 积分预扣 |
| `SETTLE` | 积分消耗 |
| `RELEASE` | 预扣释放 |
| `REFUND` | 积分退回 |

未知类型直接显示原始值，避免新类型被静默误标。

商业权益发放的识别基于现有商业记账幂等键约定：一次性积分包使用 `order:` 前缀，订阅周期积分使用 `subscription:` 前缀。其他 `GRANT` 流水继续作为历史手工增加返回。

### 充值中心界面

将“权益发放记录”卡片替换为“积分明细”卡片，表格字段为：

- 变化类型
- 变动积分
- 变动后余额
- 说明
- 时间

变动积分使用正负颜色区分；数值沿用本地化格式。充值中心顶部余额继续来自团队积分账户接口。原先跳转到团队设置页的“积分明细”按钮移除，因为明细已在当前页面展示。

### 团队设置界面

删除整个“团队积分”卡片，包括可用积分、累计获得、累计消耗和积分流水表格。页面加载流程只请求团队资料；团队所有者仍按现有逻辑继续请求成员列表。相关积分状态、类型导入和 service 转发一并移除。

## 数据流

1. 用户进入充值中心。
2. 页面并行加载商业目录、订阅、订单、团队积分账户与团队积分流水。
3. 后端积分流水查询将商业 `GRANT` 映射为 `ENTITLEMENT_GRANT`，历史手工 `GRANT` 映射为 `ADJUST_GRANT`。
4. 页面渲染当前余额与统一积分明细。

团队设置页不再参与积分数据流。

## 错误处理

沿用页面现有加载策略。积分账户或积分流水请求失败时，由全局请求错误处理负责提示，页面结束加载状态；不新增局部重试或降级逻辑。

## 测试

- 后端接口测试：商业订单与订阅幂等键对应的 `GRANT` 返回 `ENTITLEMENT_GRANT`，普通历史 `GRANT` 仍返回 `ADJUST_GRANT`。
- 充值中心组件测试：请求积分流水、不再请求权益发放列表，并展示类型、变动值、余额、说明和时间。
- 团队设置组件测试：不请求积分账户或积分流水，页面不显示团队积分卡片。
- 运行相关前后端测试、TypeScript/Biome 检查及 Ant Design 检查。
