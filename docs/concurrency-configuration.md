# 并行配置与任务领取

入口：管理后台 → 系统管理 → 并行配置。使用数据库任务表，不引入消息队列。

## 配置含义

| 配置 | 统计范围 | 未保存时的来源 |
| --- | --- | --- |
| 团队文本、图片上限 | 每个团队、每种类型独立统计 RUNNING | `ai.execution.max-concurrent-per-tenant`，默认各 5 |
| 团队视频在途上限 | 已领取提交、外部生成中的视频 | `ai.video.max-concurrent-per-tenant`，默认 3 |
| 单模型执行配额 | 跨团队、跨实例统计同模型 RUNNING | 现有模型配额记录；新记录默认 `ai.execution.max-concurrent-per-model`，默认 4 |
| 服务商请求总并发 | 每个服务商在本 JVM 的文本、图片、视频请求总数 | `ai.provider.max-concurrency`，默认 4 |
| 文本、图片资源池 | 本实例已预留或正在执行的任务 | 原 `ai.execution.worker-threads` 拆分，默认 2 + 2 |
| 视频提交、查询资源池 | 本实例正在提交／查询的任务 | 各 1 |

页面展示数据库连接池实际最大连接数，只读，不更改 Hikari 配置。额度范围为 1–10000，资源池范围为 1–200。

调度周期与候选批量继续使用现有应用配置：文本／图片默认每 5 秒扫描，每类型每轮最多 20 个候选；视频默认每 15 秒扫描，每轮提交、查询各最多 20 个候选。资源池设置是并行上限；吞吐还受这些扫描参数、服务商响应时间和共享保护约束，增加工作线程不会自动提高扫描频率。

V141 仅创建空配置记录；首次访问不会写入或自动提高额度。管理员保存后，配置持久化至数据库；其他实例最多约 1 秒刷新。本机池和服务商上限下降时，已有任务继续，使用量降到新上限以下才继续准入。修改模型配额时同步更新已有模型额度记录；其他设置变化不覆盖已有模型额度。

## 任务路径

1. 创建任务并预留积分，状态 PENDING。视频创建也先返回排队结果。
2. 调度器先预留对应本机池名额；没有名额时不领取数据库任务。
3. 在短事务中共享锁定配置行，再锁团队／类型和模型额度行，检查 RUNNING 数并 CAS 领取。共享锁协调管理员保存配置；READ_COMMITTED 避免等待锁后读取旧快照而超额。额度行通过 upsert 直接取得写锁，避免重复插入后的锁升级竞争。
4. 提交到无等待队列的独立执行池。提交被拒绝时释放本机名额、退回 PENDING，不消耗失败重试次数。
5. 外部模型请求在数据库事务之外执行，仍经过共享服务商并发保护。
6. 文本、图片完成或失败后释放运行额度。视频被服务商接受后保持统一任务 RUNNING，但清除本机提交租约并释放提交资源；查询走独立查询池，不重复占用团队／模型额度。终态结算后释放在途额度。

视频提交结果未知时不自动重新提交，避免重复生成和扣费。已接受的视频按 `next_poll_at, id` 选择，领取后先推进下一次查询时间，避免每轮只查询最早的一批。文本、图片候选扫描会越过额度已满的团队或模型；每轮固定候选 ID 上界，持续新任务不会阻止重新扫描被跳过的旧任务。

## 部署与边界

统一切换调度实例，避免新旧调度器同时领取。迁移前暂停旧版本新任务写入，等待本机正在执行的请求结束；正常后端启动执行 V141，再部署匹配的前端。历史任务会补齐 TEXT／IMAGE／VIDEO 分类，视频理解归入 TEXT；已有外部生成中的视频继续查询。

团队和模型额度通过数据库锁跨实例协调；本机执行池、服务商请求保护均按 JVM 生效。部署多个实例时，服务商并发总量可能达到各实例上限之和。此改动未引入跨实例的服务商请求锁。

代码与本地测试不会修改线上配置；上线后仍需根据服务商限制、数据库容量和压测结果调整额度。

## 本地验证

2026-10-20：核心调度 29 项、配置与服务商限流 17 项、图片接口 19 项、视频最终相关回归 42 项、前端 54 项测试通过。资源池降低额度的用例单独再次通过。前端 Biome／TypeScript、Ant Design 检查与构建完成；现有 cookie 和静态反馈 API 警告仍存在。

事务和迁移使用 H2 验证，尚未进行 MySQL 实库并发压测。未调用付费模型，也未部署或修改线上额度。本地页面使用模拟接口验证展示与保存，真实接口另有后端权限及持久化测试。
