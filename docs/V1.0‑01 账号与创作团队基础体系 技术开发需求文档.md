# V1\.0‑01 账号与创作团队基础体系 技术开发需求文档

> 短剧制作 SaaS 平台
核心说明：本版本**不做RBAC**，优先落地基础模型：`User → 创作团队(Tenant) → 团队成员(TenantMember) → 当前团队上下文`；明确不自动创建组织、角色、项目等业务对象，为后续V1\.0‑02 RBAC权限体系打好底层底座。

## 1\. 文档基本信息

|项目|内容|
|---|---|
|产品|短剧制作 SaaS 平台|
|版本|V1\.0‑01|
|模块|账号与创作团队基础体系|
|文档类型|技术开发需求文档|

|核心原则|一个用户可加入多个创作团队|

## 2\. 建设目标

V1\.0‑01主要解决以下业务问题：

### 2\.1 用户如何进入平台

- 用户自主注册

- 用户登录

- 用户退出登录

- 用户账号状态管理

### 2\.2 用户如何创建创作团队

用户注册后可创建自己的创作团队；创建成功，该用户自动成为团队 **Owner / 团队所有者**。

### 2\.3 用户如何加入其他团队

- 团队发起邀请

- 用户接受邀请

- 加入团队

- 被移出团队

- 主动退出团队

### 2\.4 一个用户支持多个团队

示例结构：

```Plaintext
张三
│
├── 星河影视
│   └── Owner
│
├── 蓝海传媒
│   └── Member
│
└── XX工作室
    └── Member
```

> 同一个平台账号，无需重复注册，可归属多个创作团队。

### 2\.5 用户可以切换当前团队

登录后，用户在自己加入的团队中选定当前团队，进入对应工作空间。

```Plaintext
User
 ↓
多个 TenantMember
 ↓
选择当前团队
 ↓
进入 Workspace
```

### 3\.2 本版本明确不包含

#### 3\.2\.1 RBAC权限体系

暂不实现：自定义角色、菜单权限、API权限、按钮权限、数据权限。

> 仅保留两种基础身份：`Owner`、`Member`。

#### 3\.2\.2 组织架构

暂不实现部门层级组织架构，放到后续版本迭代。

```Plaintext
公司
 ├── 制片部
 ├── 编剧部
 └── 后期部
```

#### 3\.2\.3 项目管理

暂不实现：创建项目、项目成员、项目角色、剧本、剧集、素材。

#### 3\.2\.4 SaaS商业化

暂不实现：套餐、订阅、配额、用量、计费、支付。

#### 3\.2\.5 禁止自动初始化业务对象

> 重要开发规则：**创建团队仅生成 Tenant \+ TenantMember，不自动生成任何其他业务对象**

- 不自动创建：`Organization`、`Role`、`Project`、`Script`、`WorkspaceData`

## 7\. 用户注册

### 7\.1 注册方式

V1\.0：手机号\+验证码注册；
预留扩展：邮箱、微信、Google、Apple、企业微信、飞书。

### 7\.2 注册流程

```Plaintext
输入手机号
 ↓
发送验证码
 ↓
验证验证码
 ↓
填写昵称
 ↓
设置密码
 ↓
创建User记录
 ↓
注册成功
```

### 7\.3 手机号唯一性约束

`mobile` 设置唯一索引，一个手机号只能对应一条User记录。

## 8\. 用户登录

- V1\.0支持：手机号 \+ 密码

- 预留扩展：手机号验证码登录、邮箱密码、第三方登录、SSO

## 9\. 登录完成后的团队判断逻辑

登录成功，查询当前用户全部有效的`TenantMember`关系：

1. **无团队（0条）**：跳转【创建或加入创作团队】页面

2. **仅有1个团队**：自动切入该团队工作空间

3. **多个团队（\>1）**：跳转【选择创作团队】页面

## 10\. 创建创作团队

### 10\.1 创建入口

- 注册完成后

- 我的团队页面

- 团队切换下拉菜单

### 10\.2 创建表单字段

|字段|必填|说明|
|---|---|---|
|团队名称|是|创作团队名称|
|团队类型|是|企业 / 工作室 / 个人 / 其他|
|Logo|否|团队Logo图片地址|
|团队简介|否|团队介绍文本|

### 10\.3 团队名称规则

- 长度：2‑50字符

- 禁止纯空格、全部特殊字符

- 团队名称不做全局唯一，不作为系统唯一标识

### 10\.4 团队编码规则

系统自动生成两套标识，用户不可编辑：

- `tenant_id`：数据库自增ID，例：`10000001`

- `tenant_code`：随机业务编码，例：`T8F3K92A`

### 10\.5 创建团队业务逻辑

> **必须事务包裹**

```Plaintext
User发起创建
 ↓
开启事务
 ↓
新建 Tenant
 ↓
新建 TenantMember，member_type=OWNER，status=ACTIVE
 ↓
提交事务
```

> 事务失败则全部回滚，杜绝出现“团队存在但是没有Owner”脏数据。
创建团队**只生成Tenant、TenantMember，不生成任何其他业务对象**。

## 12\. TenantMember 团队成员模型（核心表）

### 12\.1 成员表字段

|字段|类型|说明|
|---|---|---|
|id|bigint|成员关系ID|
|tenant\_id|bigint|团队ID|
|user\_id|bigint|用户ID|
|member\_type|varchar|`OWNER` / `MEMBER`|
|status|tinyint|`ACTIVE` / `REMOVED`|
|joined\_at|datetime|加入时间|
|invited\_by|bigint|邀请人user\_id|

联合唯一索引：`UNIQUE(tenant_id, user_id)`

## 13\. 成员邀请能力

### 13\.1 邀请发起

仅团队Owner可发起邀请；V1\.0使用手机号作为邀请目标。

```Plaintext
输入手机号
 ↓
校验用户是否已经注册
 ↓
创建 tenant_invitation 邀请记录
 ↓
生成随机邀请Token
 ↓
下发邀请（链接）
```

### 13\.2 tenant\_invitation 邀请表字段

|字段|说明|
|---|---|
|id|邀请ID|
|tenant\_id|团队ID|
|invite\_mobile|被邀请手机号|
|invite\_user\_id|已注册用户则填写用户ID|
|invited\_by|邀请人user\_id|
|token|邀请访问Token|
|status|邀请状态|
|expired\_at|过期时间|
|accepted\_at|接受时间|
|created\_at|创建时间|

### 13\.3 邀请状态枚举

- `PENDING`：待接受

- `ACCEPTED`：已接受

- `REJECTED`：已拒绝

- `EXPIRED`：已过期

- `CANCELLED`：管理员手动取消

### 13\.4 接受邀请两条分支

1. **用户已注册账号**

```Plaintext
打开邀请链接
 ↓
登录账号
 ↓
确认加入团队
 ↓
事务更新邀请状态 + 创建TenantMember
 ↓
加入成功
```

2. **用户尚未注册**

```Plaintext
打开邀请链接
 ↓
完成账号注册
 ↓
系统自动识别未处理的邀请记录
 ↓
事务更新邀请状态 + 创建TenantMember
 ↓
加入成功
```

### 13\.5 邀请安全约束

- Token高强度随机、不可预测

- 默认有效期7天，支持后续配置

- 单次使用，接受/拒绝后Token立即失效

## 14\. 成员管理操作

### 14\.1 移除成员（Owner操作）

```Plaintext
Owner打开成员管理
 ↓
选中成员，二次确认弹窗
 ↓
TenantMember.status = REMOVED
```

> 逻辑状态变更，**不物理删除记录**。

### 14\.2 成员主动退出团队（普通Member）

```Plaintext
我的团队 → 团队设置 → 退出团队
 ↓
二次确认
 ↓
TenantMember.status = REMOVED
```

### 14\.3 Owner退出限制

- 团队仅有Owner时，禁止直接退出；

- 提示文案：`你是当前团队所有者，请先将团队所有权转让给其他成员。`

### 14\.4 团队所有权转让（V1\.0实现）

> 需要事务保证数据一致性

```Plaintext
团队设置 → 所有权转让
 ↓
选择团队内其他成员，确认提交
 ↓
原Owner：member_type 更新为 MEMBER
 ↓
目标成员：member_type 更新为 OWNER
```

## 16\. TenantContext 后端上下文

> V1\.0‑01基础版本，后续V1\.0‑02 RBAC扩展角色权限字段

```Plaintext
TenantContext {
    userId
    tenantId
    memberId
}
```

### 16\.1 HTTP请求链路标准流程

```Plaintext
HTTP Request
     ↓
Authentication身份认证
     ↓
UserContext 用户上下文
     ↓
TenantContext 团队上下文
     ↓
校验Tenant团队状态
     ↓
校验TenantMember成员有效性
     ↓
Controller
     ↓
Service
     ↓
Repository
```

### 16\.2 租户隔离硬性规则

1. **所有业务数据表必须携带 ****`tenant_id`**（project、script、episode、material、task等）；

2. 业务查询强制拼接条件：`WHERE tenant_id = currentTenantId`；

3. **禁止信任前端传入的tenantId参数**；后端必须校验：当前登录用户的TenantMember是否属于该tenantId，校验不通过返回403，防止越权访问其他团队数据。

> 反例：`GET /api/project?tenantId=10002`，不能直接使用query里的tenantId。

## 19\. 异常场景与提示文案

|异常场景|处理\&提示|
|---|---|
|用户没有加入任何团队|提示：`你还没有加入任何创作团队，请创建团队或接受团队邀请。`|
|目标团队已禁用|提示：`当前创作团队已被停用，暂时无法进入。`|
|邀请链接已过期|提示：`该邀请已过期，请联系团队管理员重新发送邀请。`|
|用户已经是该团队成员|提示：`你已经是该创作团队成员，无需重复加入。`|
|重复发起对同一个人的邀请|不新增邀请记录；提示：`该用户已有待处理邀请。`|
|Owner直接点击退出团队|拦截操作；提示：`团队所有者不能直接退出，请先转让团队所有权。`|
|被移除成员访问原团队接口|后端返回403；前端提示：`你已不再是该创作团队成员。`|

## 20\. 安全要求

1. **密码存储**：禁止明文，推荐 `Argon2id`，备选 BCrypt；

2. **短信验证码**：设置有效期、最大尝试次数、发送频率防刷、单次使用；

3. **登录安全**：登录失败次数限制，预留IP/设备风控；使用Access‑Token \+ Refresh‑Token模型，支持强制踢下线；

4. **邀请Token**：高强度随机串、有效期、一次性消费，全部服务端校验。

## 21\. V1\.0‑01必需数据库表

- `user` 用户主表

- `tenant` 创作团队表


## 23\. 必须事务化的业务操作

1. 创建团队：创建Tenant \+ 创建TenantMember

2. 接受邀请：更新invitation状态 \+ 创建TenantMember

3. 团队所有权转让：更新新旧两条TenantMember记录

> 全部操作必须保证原子性，失败完整回滚。

## 24\. 操作日志埋点要求

需要记录的操作事件：注册、登录、退出、创建团队、修改团队、邀请成员、接受邀请、拒绝邀请、移除成员、退出团队、转让Owner、切换团队。

日志字段至少包含：
`user_id`、`tenant_id`、`operation`、`target_id`、`result`、`ip`、`user_agent`、`created_at`

## 25\. 验收标准

### 用户注册

- 用户可以手机号完成注册

- 同一手机号不可重复注册

- 验证码校验通过才可注册

- 密码非明文存储

- 注册成功生成唯一User记录

### 创作团队

- 用户可正常创建创作团队

- 创建成功自动成为团队Owner

- 一个用户可创建多个创作团队

- 创建团队不会自动生成组织、项目、角色对象

### 多团队能力

- 用户可加入多个不同创作团队

- 可查看我加入的全部团队列表

- 支持切换当前工作团队

- 各团队成员关系互相独立，团队上下文隔离

### 成员管理

- Owner可以发起成员邀请

- 用户可以接受/拒绝团队邀请

- Owner可移除普通成员

- Member可以主动退出团队

- Owner禁止直接退出团队，支持所有权转让

### 数据隔离安全

- 用户仅可访问自己所属团队的数据

- 不能通过篡改前端tenantId越权访问其它团队

- 被移除成员无法访问原团队接口

- 禁用状态团队全部成员无法进入

- 全部业务数据表绑定tenant\_id字段
