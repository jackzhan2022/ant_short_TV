# 项目 52 页面接口延迟排查

排查日期：2026-10-20。范围：`GET /api/projects/52` 与 `GET /api/projects/52/script-page-workspace`。本次只读检查，未修改线上配置、业务数据或应用代码。

## 结论

当前证据指向数据库大字段重复读取及结果传输波动。没有发现采样时连接池耗尽；对照查询的数据库执行计划也没有显示秒级扫描开销。不能将历史接口的全部 15 秒都归因于同一个已证实原因，仍需完整请求期间的连接获取与逐条 JDBC 耗时才能精确分摊。

## 实测拆分

| 环节 | 结果 | 含义 |
| --- | --- | --- |
| 新建数据库连接并 SELECT 1 | 50.77～67.20 ms | 当前新建连接没有出现秒级等待；包含客户端启动、握手和若干会话命令 |
| 复用同一连接 SELECT 1 | 4.24～4.32 ms | 小结果往返稳定；不包含应用连接池 |
| 读取项目全文后在数据库内计算 MD5，只返回 32 字符 | 9.34～9.57 ms | 包含测量结束标记的额外一次往返；读取全文数据本身可快速完成 |
| 同一连接返回项目全文 | 443.10～470.84 ms | 与小结果对比，明显延迟出现在返回较大数据时 |
| 同一连接生成并返回 256 KiB 测试字符串 | 21.45、333.21、296.10 ms | 不访问业务表也能复现大结果延迟波动，支持链路/结果传输因素 |
| 项目主键读取 EXPLAIN ANALYZE | 常量行获取 | 未发现秒级扫描 |
| 剧本、版本对照查询 EXPLAIN ANALYZE | 约 0.626、0.719 ms | 对照查询各表仅约 35 行；不是历史请求 26 条 SQL 的完整复现 |
| JVM 线程栈采样 | Hikari 获取连接等待线程 0；MySQL socket 读取线程 1 | 只代表该时刻，不能证明历史慢请求从未发生连接池排队 |

数据库 profiling 中，较慢的全文返回可在 `executing` 阶段计入约 0.89～1.20 秒。该阶段也可能包含结果发送，不能直接解释为数据库扫描执行慢。结合全文摘要与人工生成大结果的对照，传输因素更明显。采样中的 `System lock` 仅约 0.004～0.005 ms。

## 代码中的放大因素

1. `ProjectMapper.selectByTenantIdAndId` 默认读取整个项目实体，包含 `initial_script_content`。项目 52 在第一次测量时该字段约 271 KB。
2. `ProjectAccessResolver.requireView` 在权限检查时也调用上述完整实体查询。
3. 项目详情调用链包括控制器权限切面、服务读取项目和组装响应时再次检查权限，存在三处完整项目读取路径。此处是源码调用链分析，未在历史请求上逐条计数。
4. 剧本页同样经过控制器与服务两层项目权限检查，并读取当前剧本全文。
5. 剧本版本列表通过 `ScriptVersionMapper.selectByScript` 读取完整版本实体，随后响应只保留摘要字段；读取的版本正文没有用于版本列表响应。

数据库到应用的传输量因此可能大于浏览器看到的响应体。浏览器响应是否开启 gzip 也不能消除前面的数据库传输成本。

- 当前账号无法读取 `performance_schema` 的锁等待和语句摘要表；未调整权限或日志设置。
- 排查期间观察到运行实例发生重启（后续实例启动于 19:28:52）；本次未执行重启。历史请求与后续对照采样应分开解读。

## 优先处理顺序

1. 权限检查只读取权限所需字段，避免携带剧本全文；在同一请求内复用已校验的上下文，保持权限边界。
2. 剧本版本列表直接查询摘要列；项目基础资料和剧本全文按页面实际需要分别加载，并核对现有调用方兼容性。
3. 增加项目详情和剧本页的分段观测：连接获取、JDBC 执行、结果读取、完整请求耗时。先采样，不记录正文、密码或会话令牌。
4. 核查应用到数据库的公网连接是否可改为可达的同地域内网连接，并结合链路重传与带宽指标验证。当前 TCP 基础 RTT 约 4 ms，存在累计重传；仅凭累计值不能确认历史时段丢包率或具体限速位置。
